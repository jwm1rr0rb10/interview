## Как проходить курс

1. **Иди по порядку.** Модули 1–6 — типы данных: это словарь Redis. Модули 7–11 — паттерны, ради которых Redis используют в продакшене. Модули 12–18 — эксплуатация.
2. **Запускай каждый пример.** Открой `redis-cli` и повторяй команды. Прочитать про `WATCH` и увидеть, как `EXEC` вернул `(nil)`, потому что второй клиент изменил ключ, — разные уровни понимания.
3. **Ломай.** Поставь `maxmemory` поменьше и посмотри на вытеснение. Удали блокировку чужим ключом. Запусти `KEYS *` на миллионе ключей и посмотри на задержку остальных клиентов.
4. **Думай о памяти и сложности.** У каждой команды в документации указана сложность: `O(1)`, `O(log N)`, `O(N)`. В Redis одна медленная команда останавливает всех.
5. **Отвечай на вопросы в конце модуля** вслух, как на собеседовании.
6. **Сделай итоговый проект.** Он собирает все темы в одну систему.

**Что нужно установить** — Docker и Python 3:

```bash
git clone <ссылка на этот репозиторий> redis-course && cd redis-course

docker run -d --name rediscourse -p 6379:6379 redis:8.10
docker exec -it rediscourse redis-cli          # интерактивный redis-cli
python3 examples/run_tests.py                  # прогнать все примеры курса
```

Сценарий примера — это обычные команды `redis-cli`, по одной в строке. Несколько клиентов обозначены префиксами `[B]`, `[C]`: это отдельные соединения, как второй терминал с `redis-cli`. Повторить сценарий руками можно в двух окнах `redis-cli`.

Все листинги с указанным файлом — настоящие ответы сервера Redis 8.10.3: сценарии выполнены, а тесты сверяют вывод при каждом запуске. # Модуль 0. Что такое Redis и зачем он нужен

## 0.1 Определение простыми словами

**Redis** (REmote DIctionary Server) — хранилище структур данных в оперативной памяти. Клиенты подключаются к серверу по сети и выполняют команды над ключами, а значения — не просто строки, а списки, хеши, множества, сортированные множества, потоки, геоиндексы, векторы и другие типы. Каждая команда работает за предсказуемое время, чаще всего за микросекунды.

Три вещи, которые нужно понять сразу:

1. **Данные живут в памяти.** Поэтому Redis быстрый, и поэтому весь набор данных должен помещаться в RAM. На диск Redis пишет снимки (RDB) и журнал (AOF), но это способ пережить перезапуск, а не основное хранилище.
2. **Команды выполняются по одной.** Основной поток обрабатывает команды строго последовательно, поэтому каждая команда атомарна, а гонок внутри сервера нет. Обратная сторона: одна медленная команда задерживает всех клиентов.
3. **Redis — это не «просто кэш».** Это набор атомарных операций над структурами данных: счётчики, очереди, таблицы лидеров, блокировки, ограничение частоты, журналы событий. Кэш — лишь самый популярный сценарий.

История: Redis создал Сальваторе Санфилиппо (antirez) в 2009 году, чтобы ускорить свой сервис веб-аналитики. Проект быстро стал стандартом де-факто для кэша и быстрых структур данных; развивает его компания Redis Ltd.

## 0.2 Лицензии, Valkey и Redis 8

Эту историю спрашивают на собеседованиях и обсуждают при выборе технологии:

| Год | Событие |
|---|---|
| 2009–2024 | Redis под лицензией BSD — свободное использование где угодно |
| Март 2024 | Redis 7.4 переходит на RSALv2 и SSPLv1 — облачные провайдеры теряют право предлагать Redis как сервис без договора |
| Март 2024 | Linux Foundation и облачные провайдеры создают форк **Valkey** от Redis 7.2.4 под BSD |
| Ноябрь 2024 | Сальваторе Санфилиппо возвращается в Redis Ltd |
| Май 2025 | **Redis 8.0** добавляет третий вариант лицензии — **AGPLv3**, признанную OSI свободной; продукт называется Redis Open Source и включает JSON, поиск, временные ряды и вероятностные структуры |
| 2025–2026 | Redis выпускает минорные версии каждые три месяца: 8.2, 8.4, 8.6, 8.8, **8.10** (июль 2026), 8.12 — в стадии release candidate |

Для приложения всё это почти не важно: протокол и базовые команды Redis и Valkey совместимы. Различия — в новых командах (большинство нововведений Redis 8 из этого курса есть только в Redis), в лицензии и в том, что предлагает твой облачный провайдер (AWS ElastiCache и Google Memorystore предлагают Valkey наравне с Redis или вместо него).

## 0.3 Чем Redis хорош, а чем нет

| Свойство | Как в Redis |
|---|---|
| Скорость | Сотни тысяч операций в секунду на ядро, задержка — доли миллисекунды |
| Структуры данных | Богатый набор с атомарными операциями над ними |
| Простота | Сервер запускается одной командой, протокол текстовый, команды читаются как глаголы |
| Объём данных | Ограничен оперативной памятью; терабайты — только кластером и дорого |
| Надёжность хранения | Настраиваемая: от «потерять всё при перезапуске» до «потерять не больше секунды»; гарантий как у PostgreSQL нет |
| Запросы | Только по ключу и структурам; произвольных `WHERE` и JOIN нет (кроме модуля поиска) |
| Транзакции | Атомарность группы команд есть, отката нет |
| Масштабирование | Реплики для чтения; Cluster шардирует ключи, но запрещает операции над ключами разных слотов |

## 0.4 Redis и альтернативы

| Критерий | Redis | Valkey | Memcached | PostgreSQL | Kafka | Dragonfly, KeyDB, Garnet |
|---|---|---|---|---|---|---|
| Модель | Структуры данных в памяти | То же, форк Redis 7.2 | Простой кэш ключ-значение | Реляционная база на диске | Распределённый журнал | Redis-совместимые серверы |
| Типы данных | Богатые + модули | Богатые | Только строки | Таблицы, JSON | Сообщения | Подмножество команд Redis |
| Персистентность | RDB, AOF | RDB, AOF | Нет | Полная | Полная, с репликацией | Разная |
| Многопоточность | Команды в одном потоке, ввод-вывод в нескольких | Многопоточный ввод-вывод | Многопоточный | Процессы | Распределённый | Многопоточные |
| Лучше всего для | Кэш, счётчики, очереди, лимиты, сессии, лидерборды, real-time | То же, где нужна BSD-лицензия или облачный сервис на Valkey | Простой кэш строк | Источник истины | Поток событий с долгим хранением и переигрыванием | Замена Redis на больших машинах |

**Главное правило:** Redis — не источник истины для данных, которые нельзя потерять, если ты осознанно не настроил персистентность, репликацию и не принял их пределы. Деньги, заказы и пользователи живут в базе данных; Redis ускоряет и координирует.

## 0.5 Где Redis используют

| Сценарий | Структура |
|---|---|
| **Кэш** запросов к базе и внешним API | Строки, хеши с TTL |
| **Сессии** пользователей | Хеши с TTL, время жизни отдельных полей |
| **Ограничение частоты** запросов | `INCREX`, строки с `INCR` + `EXPIRE`, сортированные множества |
| **Таблицы лидеров** и рейтинги | Сортированные множества |
| **Очереди** и фоновые задачи | Списки (`LMOVE`), потоки с группами потребителей |
| **Журнал событий**, event sourcing на коротком горизонте | Потоки |
| **Распределённые блокировки** и координация | `SET NX PX`, `DELEX IFEQ` |
| **Уникальные посетители**, аналитика в реальном времени | HyperLogLog, битовые карты |
| **Геопоиск** «рядом со мной» | Геоиндексы |
| **Чаты и уведомления** в реальном времени | Pub/Sub, потоки |
| **Семантический кэш и векторный поиск** для AI | Vector Set, модуль поиска |

## 0.6 Когда Redis не нужен

- **Данные больше памяти** и не делятся на горячие и холодные — дешевле база данных с кэшем страниц.
- **Нужны сложные запросы, JOIN и строгие транзакции** — это работа реляционной базы.
- **Долгое хранение событий и переигрывание за недели** — Kafka или аналоги.
- **Кэш, который всё равно никто не читает**: перед внедрением измерь, что именно медленно; иногда достаточно индекса в базе.
- **Ещё один компонент без пользы**: Redis нужно мониторить, обновлять и резервировать, как любой другой сервис.

## 0.7 Словарь на одну страницу

| Термин | Коротко |
|---|---|
| **Ключ** | Имя значения, бинарно-безопасная строка: `user:42:profile` |
| **TTL** | Время жизни ключа, после которого он удаляется |
| **Кодировка** | Внутреннее представление типа: `listpack`, `hashtable`, `intset`, `skiplist` |
| **RESP** | Протокол Redis: RESP2 и RESP3 |
| **Пайплайн** | Отправка многих команд без ожидания ответа на каждую |
| **RDB, AOF** | Снимок памяти и журнал команд на диске |
| **Реплика** | Копия данных основного сервера, обновляемая асинхронно |
| **Sentinel** | Система наблюдения и автоматического переключения на реплику |
| **Cluster** | Шардирование ключей по 16 384 хеш-слотам на нескольких серверах |
| **Вытеснение** | Удаление ключей при достижении `maxmemory` по выбранной политике |

## 1.2 redis-cli

```bash
redis-cli                                   # интерактивный режим, localhost:6379
redis-cli -h host -p 6379 -a password      # с паролем (лучше через REDISCLI_AUTH)
redis-cli -u redis://user:pass@host:6379/0 # URI

redis-cli --pipe < commands.txt             # массовая загрузка
```

В интерактивном режиме есть подсказки синтаксиса и `HELP команда`. Графические клиенты: **Redis Insight** (официальный, бесплатный), Another Redis Desktop Manager, расширения для IDE.

## 1.3 Первые команды

```
# файл: examples/01_basics/first_steps.redis — вывод сценария
# Проверка связи и первые ключи
redis> PING
PONG
redis> SET greeting "Hello, Redis"
OK
redis> GET greeting
"Hello, Redis"
redis> GET missing
(nil)
redis> EXISTS greeting missing
(integer) 1
redis> TYPE greeting
string

# Пространство ключей: двоеточие — соглашение для иерархии имён
redis> SET user:42:name anya
OK
redis> SET user:42:city kazan
OK
redis> DBSIZE
(integer) 3
redis> DEL user:42:city
(integer) 1
redis> DBSIZE
(integer) 2

# RENAME атомарно переименовывает, COPY — копирует (Redis 6.2+)
redis> RENAME greeting hello
OK
redis> COPY hello hello:backup
(integer) 1
redis> GET hello:backup
"Hello, Redis"

# Время жизни ключа
redis> SET session:abc token-123 EX 300
OK
redis> TTL session:abc
(integer) 300
redis> TTL hello
(integer) -1
redis> TTL missing
(integer) -2
redis> PERSIST session:abc
(integer) 1
redis> TTL session:abc
(integer) -1

# UNLINK удаляет ключ из пространства имён сразу, а память освобождает в фоне
redis> UNLINK hello hello:backup
(integer) 2

# Ошибка типа: команда для строк к списку
redis> RPUSH tasks t1 t2
(integer) 2
redis> GET tasks
(error) WRONGTYPE Operation against a key holding the wrong kind of value
redis> TYPE tasks
list
redis> OBJECT ENCODING tasks
"listpack"
```

Что здесь важно:

- **Ключ — бинарно-безопасная строка** до 512 МБ, но использовать стоит короткие и понятные имена. Соглашение — части через двоеточие: `тип:идентификатор:поле` — `user:42:name`, `cache:product:1001`, `ratelimit:api:user42:2026-11-06T12`.
- **У каждого ключа один тип.** Команда не того типа — ошибка `WRONGTYPE`. `TYPE` показывает тип, `OBJECT ENCODING` — внутреннее представление (модуль 12).
- **TTL**: `-1` — ключ без срока жизни, `-2` — ключа нет. Срок задаётся при записи (`SET ... EX`) или отдельно (`EXPIRE`, `PEXPIRE`, `EXPIREAT`), снимается `PERSIST`. Большинство команд записи **сбрасывают** TTL при перезаписи ключа (`SET` без `KEEPTTL`), а изменение структуры (`HSET`, `LPUSH`) — нет.
- **`DEL` против `UNLINK`**: `DEL` освобождает память синхронно — удаление ключа с миллионом элементов остановит сервер на заметное время. `UNLINK` убирает ключ мгновенно, а память освобождает в фоновом потоке.

## 1.4 Как Redis удаляет просроченные ключи

```
ленивое удаление:  клиент обращается к ключу → срок истёк → ключ удаляется, ответ (nil)
активное удаление: фоновый цикл (hz раз в секунду) берёт выборку ключей с TTL
                   и удаляет просроченные; если их много — повторяет цикл
```

Поэтому просроченный ключ может ещё какое-то время занимать память, но **никогда не будет возвращён клиенту**. На реплике просроченные ключи удаляет не она сама, а команда `DEL`, пришедшая от мастера, хотя чтение просроченного ключа с реплики тоже вернёт `(nil)`.

## 1.5 Обход ключей: SCAN, а не KEYS

`KEYS pattern` проходит **все** ключи за один вызов: на базе с десятками миллионов ключей это секунды, в течение которых сервер не обслуживает никого. В продакшене `KEYS` запрещают через ACL.

```
redis> SCAN 0 MATCH user:* COUNT 1000
1) "1835"                 ← курсор для следующего вызова
2) 1) "user:42:name"      ← порция ключей
   2) "user:17:name"
redis> SCAN 1835 MATCH user:* COUNT 1000
...                       ← повторять, пока курсор не станет "0"
```

Гарантии `SCAN`: ключ, существовавший всё время обхода, будет возвращён хотя бы один раз; возможны повторы; порядок не определён; `COUNT` — подсказка, а не точное число. Для коллекций есть `HSCAN`, `SSCAN`, `ZSCAN`. Тип можно отфильтровать: `SCAN 0 TYPE stream`.

## 1.6 Базы данных 0–15

Redis поддерживает несколько логических баз (`SELECT 1`), но это не изоляция: общая память, общие настройки, Redis Cluster поддерживает только базу 0. Для разных приложений запускай отдельные экземпляры Redis или используй префиксы ключей и ACL.

## 1.7 Типичные ошибки первого дня

| Симптом | Причина | Что делать |
|---|---|---|
| `Could not connect to Redis at 127.0.0.1:6379: Connection refused` | Сервер не запущен или слушает другой адрес | `docker ps`, `bind`, `port` в конфигурации |
| `NOAUTH Authentication required` | Включён пароль или ACL | `AUTH user password`, `-a`, `REDISCLI_AUTH` |
| `WRONGTYPE Operation against a key holding the wrong kind of value` | Команда не для типа ключа | `TYPE key`, разные имена ключей для разных типов |
| Ключ «пропал» | Истёк TTL, вытеснен по `maxmemory`, перезапуск без персистентности | `TTL`, `INFO stats` (`expired_keys`, `evicted_keys`), настройки персистентности |
| Сервер замер на секунды | `KEYS *`, `DEL` огромного ключа, `FLUSHALL` | `SCAN`, `UNLINK`, `FLUSHALL ASYNC` |
| `DENIED Redis is running in protected mode` | Подключение извне без пароля | Настроить пароль/ACL и `bind`, а не отключать protected mode |

# Модуль 2. Строки, счётчики и время жизни

## 2.1 Строка — самый универсальный тип

Строка в Redis — бинарно-безопасный массив байт до 512 МБ: текст, число, JSON, сериализованный объект, картинка. Числа в строках поддерживают атомарную арифметику, а маленькие строки хранятся компактно.

| Кодировка | Когда | Зачем |
|---|---|---|
| `int` | Значение — целое 64-битное число | Хранится как число, без строки |
| `embstr` | Строка до 44 байт | Значение лежит в одном блоке памяти вместе с заголовком объекта |
| `raw` | Длиннее или изменялась (`APPEND`, `SETRANGE`) | Отдельный буфер |

## 2.2 Все операции со строками

```
# файл: examples/02_strings/strings.redis — вывод сценария
# SET с условиями и временем жизни
redis> SET lock:report owner-1 NX EX 30
OK
redis> SET lock:report owner-2 NX EX 30
(nil)
redis> GET lock:report
"owner-1"
redis> SET config:mode dark XX
(nil)
redis> SET config:mode dark
OK
redis> SET config:mode light XX GET
"dark"

# Сравнение со значением при записи и удалении (Redis 8.4): compare-and-set без Lua
redis> SET balance 100
OK
redis> SET balance 70 IFEQ 100
OK
redis> SET balance 50 IFEQ 100
(nil)
redis> GET balance
"70"
redis> DELEX balance IFEQ 999
(integer) 0
redis> DELEX balance IFEQ 70
(integer) 1
redis> EXISTS balance
(integer) 0

# Счётчики: атомарно, без гонок «прочитал — прибавил — записал»
redis> INCR page:views
(integer) 1
redis> INCRBY page:views 10
(integer) 11
redis> DECR page:views
(integer) 10
redis> INCRBYFLOAT rating 4.5
"4.5"
redis> INCRBYFLOAT rating -0.25
"4.25"
redis> SET name anya
OK
redis> INCR name
(error) ERR value is not an integer or out of range

# INCREX (Redis 8.8): инкремент с границами и временем жизни одной командой
redis> INCREX api:calls:user42 BYINT 1 UBOUND 3 EX 60
1) (integer) 1
2) (integer) 1
redis> INCREX api:calls:user42 BYINT 1 UBOUND 3 EX 60
1) (integer) 2
2) (integer) 1
redis> INCREX api:calls:user42 BYINT 1 UBOUND 3 EX 60
1) (integer) 3
2) (integer) 1
redis> INCREX api:calls:user42 BYINT 1 UBOUND 3 EX 60
1) (integer) 3
2) (integer) 0
redis> TTL api:calls:user42
(integer) 60

# Пачки ключей за один запрос
redis> MSET price:mug 450 price:tee 1290 price:cap 990
OK
redis> MGET price:mug price:cap price:none
1) "450"
2) "990"
3) (nil)
redis> MSETNX price:mug 1 price:new 2
(integer) 0
redis> MGET price:mug price:new
1) "450"
2) (nil)

# MSETEX (Redis 8.4): несколько ключей с общим временем жизни
redis> MSETEX 2 otp:a 111111 otp:b 222222 EX 120
(integer) 1
redis> TTL otp:b
(integer) 120

# GETEX и GETDEL: прочитать и изменить время жизни или удалить
redis> SET token abc
OK

"abc"

(integer) 60
redis> GETDEL token
"abc"

(integer) 0

# Строки как байтовые массивы
redis> SET log "2026-11-06 "
OK

"ERROR"

redis> SET s "short text"

redis> OBJECT ENCODING s

```

## 2.3 Что здесь важно

- **`SET ... NX EX 30`** — атомарно «создай, если нет, со сроком жизни». Основа блокировок и защиты от двойной обработки (модуль 10). Отдельные `SETNX` + `EXPIRE` — две команды, между которыми процесс может упасть и оставить вечную блокировку.
- **`SET ... GET`** возвращает старое значение, заменяя устаревшую команду `GETSET`.
- **`SET ... IFEQ значение` и `DELEX ... IFEQ значение`** (Redis 8.4) — запись и удаление «только если текущее значение равно ожидаемому»: compare-and-set без `WATCH` и без Lua. Варианты `IFNE`, а также `IFDEQ`/`IFDNE` сравнивают не само значение, а его хеш (`DIGEST` возвращает XXH3-хеш) — удобно для больших значений.
- **`INCR`, `INCRBY`, `INCRBYFLOAT`** атомарны: тысяча клиентов, одновременно увеличивающих счётчик, не потеряют ни одного инкремента. Для дробных значений помни про неточность плавающей точки — деньги считай в копейках через `INCRBY`.
- **`INCREX`** (Redis 8.8) объединяет инкремент, границы (`LBOUND`, `UBOUND`), режим насыщения (`SATURATE`) и время жизни. Ответ — пара: новое значение и фактически применённый инкремент. Когда граница достигнута, инкремент не применяется и возвращается `0` — готовый ограничитель «не больше N за окно» одной командой.
- **`MSET`/`MGET`** — один сетевой обмен вместо многих. `MSETNX` записывает **все** ключи или **ни одного**. `MSETEX` (Redis 8.4) задаёт общий TTL пачке ключей.
- **`GETEX`** читает и продлевает или снимает срок жизни, **`GETDEL`** — читает и удаляет (одноразовые токены).
- **Время жизни** при перезаписи `SET` сбрасывается, если не указан `KEEPTTL`.

## 2.4 Время жизни: правила и ловушки

| Действие | Что происходит с TTL |
|---|---|
| `SET key v` | Сбрасывается (ключ становится вечным) |
| `SET key v KEEPTTL` | Сохраняется |
| `INCR`, `APPEND`, `SETRANGE` | Сохраняется |
| `RENAME` | Переносится на новое имя |
| `EXPIRE key 0` или отрицательное значение | Ключ удаляется |
| `EXPIRE ... NX/XX/GT/LT` (Redis 7.0) | Задать срок, только если его нет / есть / новый больше / меньше |
| `PERSIST` | Срок снимается |

**TTL с джиттером:** если 100 000 ключей кэша созданы одновременно с одинаковым TTL, они одновременно и истекут — и все запросы разом пойдут в базу. Добавляй к TTL случайную составляющую: `EX 3600 + random(0..300)` (модуль 8).

## 2.5 Строки или хеш для объекта

| Вариант | Плюсы | Минусы |
|---|---|---|
| Строка с JSON `user:42 → {...}` | Одна команда, атомарная замена, удобно для кэша | Изменение одного поля — прочитать и переписать весь объект |
| Хеш `user:42` с полями | Чтение и изменение отдельных полей, `HINCRBY`, TTL полей, компактно для маленьких объектов | Нет вложенности |
| Отдельные ключи `user:42:name` | Разный TTL у каждого поля | Много ключей, накладные расходы на каждый ключ ~50–70 байт |
| JSON-тип (модуль) `JSON.SET user:42 $ ...` | Вложенность, обновление по пути, индексация поиском | Нужен модуль; дороже по памяти, чем хеш |

## 2.6 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Вечная блокировка после падения процесса | `SETNX`, затем `EXPIRE` отдельной командой | `SET key value NX PX ttl` |
| Ключ кэша перестал истекать | Перезапись через `SET` без `EX` или `KEEPTTL` | Всегда указывать TTL при записи кэша |
| `ERR value is not an integer or out of range` | `INCR` по нечисловой строке | Отдельные ключи для счётчиков |
| Потерянные инкременты | `GET`, прибавить в приложении, `SET` | `INCR`, `INCRBY`, `INCREX` |
| Сотни отдельных `GET` на страницу | Нет пакетирования | `MGET`, пайплайн |
| Одновременная лавина промахов кэша | Одинаковый TTL у массово созданных ключей | Джиттер в TTL |

# Модуль 3. Списки, хеши и множества

## 3.1 Три коллекции на каждый день

| Тип | Что это | Типичные задачи | Сложность ключевых операций |
|---|---|---|---|
| **Список** | Упорядоченная последовательность строк, вставка с обоих концов | Очереди, стеки, последние N событий, ленты | `LPUSH`/`RPOP` — O(1); доступ по индексу — O(N) |
| **Хеш** | Набор пар «поле — значение» под одним ключом | Объекты, профили, сессии, счётчики по полям | `HGET`/`HSET` — O(1); `HGETALL` — O(N) |
| **Множество** | Неупорядоченный набор уникальных строк | Теги, уникальные посетители за день, связи «подписан на», фильтры | `SADD`/`SISMEMBER` — O(1); пересечения — O(N·M) |

## 3.2 Коллекции в действии

```
# файл: examples/03_collections/collections.redis — вывод сценария
# ===== Списки: очередь, стек, последние N событий =====
```

## 3.3 Списки

- **Очередь**: `RPUSH` в хвост + `LPOP` из головы (или наоборот). **Стек**: `LPUSH` + `LPOP`.
- **Ограниченный список последних событий**: `LPUSH` + `LTRIM key 0 N-1` в одном пайплайне или транзакции.
- **Надёжная очередь**: `LMOVE source processing LEFT RIGHT` атомарно переносит элемент в список «в работе». Если воркер упал, элемент не потерян — его можно вернуть. После успешной обработки — `LREM processing 1 элемент`. Блокирующие версии `BLPOP`, `BLMOVE` ждут появления элементов, не нагружая сервер опросом (модуль 11).
- **`LMOVEM`** (Redis 8.10) переносит пачку элементов одной командой: воркер забирает сразу 100 задач.
- **Доступ по индексу и `LREM` — O(N).** Список не годится для поиска элемента в середине; для этого — множества или хеши.

## 3.4 Хеши

- **Объект с полями**: читай только нужные поля (`HMGET`), увеличивай счётчики в объекте (`HINCRBY`), проверяй и создавай поле атомарно (`HSETNX`).
- **`HGETALL` на большом хеше — O(N)** и блокирует сервер. Для хешей на тысячи полей используй `HSCAN` или `HMGET` нужных полей.
- **Время жизни полей** (Redis 7.4): `HEXPIRE`, `HPEXPIRE`, `HTTL`, `HPERSIST` — сессия с полем `csrf` на 10 минут, а сама сессия живёт сутки. Redis 8.0 добавил `HSETEX` (записать поля со сроком), `HGETEX` (прочитать и изменить срок), `HGETDEL` (прочитать и удалить поле).
- **Компактные хеши** (Redis 8.10): если много ключей-хешей имеют одинаковый набор полей (`user:1`, `user:2`, …), Redis может хранить имена полей один раз в общем шаблоне, сильно экономя память. Для массовой загрузки таких хешей появилась команда `HIMPORT`.

## 3.5 Множества

- **Уникальность из коробки**: повторный `SADD` ничего не добавляет и возвращает 0.
- **Операции над множествами**: `SINTER` (общие теги, общие друзья), `SUNION`, `SDIFF` и версии `...STORE`, сохраняющие результат. `SINTERCARD` (Redis 7.0), `SUNIONCARD` и `SDIFFCARD` (Redis 8.10) возвращают только мощность — без построения результата и с параметром `LIMIT`.
- **`SMEMBERS` на большом множестве — O(N)**: используй `SSCAN`.
- **Случайные элементы**: `SRANDMEMBER` (без удаления), `SPOP` (с удалением) — розыгрыши, выборки.
- **Порядок не гарантирован.** Маленькие множества строк в кодировке `listpack` возвращают элементы в порядке вставки, а множества из целых (`intset`) — по возрастанию, но полагаться на это нельзя: после роста множество станет хеш-таблицей с произвольным порядком.

## 3.6 Кодировки и пороги

Маленькие коллекции Redis хранит компактно — одним непрерывным блоком памяти (`listpack`), а при росте переводит в полноценные структуры:

| Тип | Компактная кодировка | Порог по умолчанию (Redis 8) | Полная кодировка |
|---|---|---|---|
| Хеш | `listpack` | `hash-max-listpack-entries 512`, `hash-max-listpack-value 64` байта | `hashtable` |
| Множество целых | `intset` | `set-max-intset-entries 512` | `hashtable` |
| Множество строк | `listpack` | `set-max-listpack-entries 128` | `hashtable` |
| Список | `listpack` | `list-max-listpack-size -2` (8 КБ на узел) | `quicklist` (связный список listpack-узлов) |
| Сортированное множество | `listpack` | `zset-max-listpack-entries 128` | `skiplist` + хеш-таблица |

Компактная кодировка экономит память в разы, но операции в ней — O(N) по размеру блока, поэтому пороги небольшие. Пример в 3.2 показывает переход хеша из `listpack` в `hashtable` на 513-м поле. Обратного перехода при уменьшении нет. Подробнее о памяти — в модуле 12.

## 3.7 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Сервер «подвисает» на чтении коллекции | `HGETALL`, `SMEMBERS`, `LRANGE 0 -1` на миллионе элементов | `HSCAN`/`SSCAN`, пагинация, ограничение размеров |
| Задачи из очереди теряются при падении воркера | `LPOP`/`BRPOP` без списка «в работе» | `LMOVE`/`BLMOVE` или потоки с подтверждениями |
| Порядок элементов множества «поменялся» | Множество выросло и сменило кодировку | Не полагаться на порядок; нужен порядок — сортированное множество |
| Сессия хранит устаревшие поля | Нет TTL полей | `HEXPIRE`, `HSETEX` |
| Большой расход памяти на миллионы мелких ключей | Объекты разложены по отдельным ключам | Хеши (и компактные хеши Redis 8.10) |
| Список используется для поиска элемента | `LPOS`/`LREM` — O(N) | Множество или хеш |

# Модуль 4. Сортированные множества

## 4.1 Что это

Сортированное множество (ZSET) — набор уникальных строк-членов, у каждого из которых есть число (score). Элементы всегда упорядочены по score, а при равенстве — лексикографически. Это самая «умная» структура Redis: таблицы лидеров, приоритетные очереди, индексы по времени, скользящие окна для ограничения частоты, автодополнение.

```
ZSET leaderboard               внутри (больше 128 элементов): skiplist + хеш-таблица
 gosha   900                    хеш-таблица: член → score       — ZSCORE за O(1)
 anya   1500                    skiplist: упорядочен по score    — ранги и диапазоны за O(log N)
 borya  1600
 vika   1800
```

## 4.2 Сортированные множества в действии

## 4.3 Что здесь важно

- **`ZADD key score member`** добавляет или обновляет score. Флаги: `NX` — только новые, `XX` — только существующие, `GT`/`LT` — обновить, только если новый score больше или меньше (лучший результат игрока), `CH` — вернуть число изменённых, а не добавленных, `INCR` — прибавить к score.
- **`ZRANGE` — универсальная команда диапазонов** (Redis 6.2): по индексам, `BYSCORE`, `BYLEX`, с `REV` и `LIMIT offset count`. Старые `ZRANGEBYSCORE`, `ZREVRANGE` и другие оставлены для совместимости.
- **Границы**: `(1600` — не включая, `-inf`/`+inf` — бесконечности, для лексикографических диапазонов `[red` — включая, `(ree` — не включая, `-`/`+` — от начала и до конца.
- **Ранг**: `ZRANK` и `ZREVRANK` — место за O(log N); с Redis 7.2 `WITHSCORE` возвращает и score.
- **Приоритетная очередь**: `ZPOPMIN`/`ZPOPMAX`, блокирующие `BZPOPMIN`, `BZMPOP`.
- **Индекс по времени**: score = unix-время. Выборка за интервал — `ZRANGE ... BYSCORE`, удаление старого — `ZREMRANGEBYSCORE key -inf <порог>`. Так делают отложенные задачи: score = время запуска, воркер забирает всё, что уже наступило.
- **Автодополнение**: все члены с одинаковым score упорядочены лексикографически, и `ZRANGE ... BYLEX` выдаёт слова с префиксом.
- **`ZUNION`, `ZINTER` и версии `...STORE`** складывают score (по умолчанию `SUM`) с весами, умеют `MIN` и `MAX`, а Redis 8.8 добавил агрегат **`COUNT`** — в скольких множествах встретился член (например, сколько недель подряд игрок был в топе).

## 4.4 Паттерны

| Задача | Как |
|---|---|
| Таблица лидеров | `ZADD ... GT`, топ — `ZRANGE 0 9 REV WITHSCORES`, место — `ZREVRANK` |
| Лидеры за период | Ключ на день или неделю + `ZUNIONSTORE` для агрегации |
| Отложенные задачи | score = время запуска; воркер: `ZRANGE ... BYSCORE -inf <now> LIMIT 0 100` + атомарный перенос через Lua |
| Скользящее окно лимита | score = время запроса; `ZREMRANGEBYSCORE` старше окна, `ZCARD`, `ZADD` (модуль 10) |
| Самые популярные товары | `ZINCRBY trending 1 <товар>` на каждый просмотр, топ — `ZRANGE ... REV` |
| Пагинация ленты по времени | score = время, `ZRANGE ... BYSCORE REV LIMIT` от последнего показанного score |

## 4.5 Точность score

Score — число двойной точности (`double`): целые до 2⁵³ представляются точно. Unix-время в миллисекундах помещается, а 64-битные идентификаторы — нет: не используй snowflake-ID как score. Для составных ключей сортировки (очки, затем время) кодируй их в одно число, например `score = очки * 10^10 + (MAX_TIME - время)`.

## 4.6 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Результат игрока уменьшился | `ZADD` без `GT` перезаписал score | `ZADD ... GT` |
| Неверный порядок при одинаковом score | Равные score сортируются лексикографически по члену | Составной score |
| Большие ID в score «поплыли» | Потеря точности `double` | ID — в члене, а не в score |
| Таблица лидеров на миллионы участников тормозит | `ZRANGE 0 -1` целиком | Только нужный диапазон, `LIMIT` |
| Индекс по времени растёт бесконечно | Нет удаления старых записей | `ZREMRANGEBYSCORE` по расписанию или при каждой записи |

# Модуль 5. Потоки (Streams) и группы потребителей

## 5.1 Что такое поток

Поток — журнал записей только на дописывание. У каждой записи есть ID вида `<миллисекунды>-<номер>` и набор полей. Потоки дают то, чего нет у списков и Pub/Sub: **хранение истории, чтение с любого места, группы потребителей с подтверждениями и повторной доставкой**.

```
stream orders
 1762400000000-0  {order_id: 1001, status: created}
 1762400000000-1  {order_id: 1002, status: created}   ← last_delivered_id группы billing
 1762400005000-0  {order_id: 1001, status: paid}

группа billing
 ├── worker-1   PEL: [1762400000000-0]    ← выдано, но не подтверждено
 └── worker-2   PEL: [1762400000000-1]
```

## 5.3 Как это работает

- **`XADD key * field value`** — `*` просит сервер сгенерировать ID из текущего времени. ID обязаны расти; явные ID в примерах — только ради воспроизводимого вывода.
- **Чтение**: `XRANGE`/`XREVRANGE` по диапазону ID, `XREAD STREAMS key <id>` — всё после ID, `XREAD BLOCK ms ... $` — ждать новых записей (`$` — «только то, что придёт после вызова»). С Redis 8.10 `MAXCOUNT` и `MAXSIZE` ограничивают суммарный объём ответа.
- **Группа потребителей** (`XGROUP CREATE`): каждое сообщение достаётся одному потребителю группы, и у разных групп своя позиция чтения. `XREADGROUP ... >` — «новые, никому не выданные»; `XREADGROUP ... 0` — «мои невыданные повторно» (свой PEL).
- **PEL** (Pending Entries List) — выданные, но не подтверждённые сообщения. `XACK` убирает из PEL. Пока сообщение не подтверждено, оно не потеряется.
- **Восстановление после сбоя**: `XAUTOCLAIM` забирает сообщения, которые висят в PEL дольше заданного времени, другому потребителю (в примере порог 0 — чтобы показать сразу). `XCLAIM` — то же для конкретных ID. Счётчик доставок помогает отправить «ядовитые» сообщения в отдельный поток ошибок после N попыток.
- **`XNACK`** (Redis 8.8) — потребитель сам возвращает сообщение в группу без подтверждения: «не могу обработать сейчас» — без ожидания тайм-аута.
- **`XACKDEL` и `XDELEX`** (Redis 8.2) подтверждают и удаляют записи с учётом других групп (`KEEPREF`, `DELREF`, `ACKED`).
- **Обрезка**: `XADD ... MAXLEN ~ 100000` или `MINID` по времени, либо отдельный `XTRIM`. С `~` Redis обрезает целыми узлами и это дёшево; точная обрезка дороже.
- **Идемпотентная запись** (Redis 8.6): `XADD ... IDMP <производитель> <ключ-идемпотентности> *` — повтор с тем же ключом (например, после тайм-аута сети) не создаёт дубликат и возвращает ID первой записи. `IDMPAUTO` вычисляет ключ по содержимому.

## 5.4 Гарантии доставки

```
производитель ──XADD──► поток ──XREADGROUP──► потребитель ──обработка──► XACK
                                         ▲                      │
                          XAUTOCLAIM ────┘   сбой до XACK ───────┘  (сообщение останется в PEL)
```

Это **at-least-once**: сообщение может быть обработано больше одного раза (упал после обработки, но до `XACK`). Обработчик должен быть **идемпотентным**: запоминать обработанные ID, использовать `SET ... NX` по ключу операции или upsert в базе.

## 5.5 Потоки, списки, Pub/Sub или Kafka

| Нужно | Выбор |
|---|---|
| Простая очередь задач, один тип воркеров | Список с `BLMOVE` |
| Несколько независимых групп обработчиков, подтверждения, повторная доставка, история | Поток с группами |
| Уведомить всех подключённых прямо сейчас, потеря допустима | Pub/Sub (модуль 11) |
| Хранить события неделями, переигрывать, огромный объём, много потребителей | Kafka |

Поток живёт в памяти: на миллионы событий в сутки нужна обрезка, а долгая история — в Kafka или базе.

## 5.6 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Память растёт без остановки | Нет обрезки потока | `MAXLEN ~` / `MINID` при `XADD` или `XTRIM` по расписанию |
| Сообщения «застряли» | Потребитель упал, PEL никто не разбирает | `XAUTOCLAIM` по расписанию, мониторинг `XPENDING` |
| Одно и то же сообщение бесконечно падает | Нет ограничения повторов | Счётчик доставок из `XPENDING`, поток «мёртвых писем» |
| Дубли при повторной отправке производителя | Повтор `XADD` после тайм-аута | `IDMP` (Redis 8.6) или дедупликация у потребителя |
| `XREADGROUP` с `0` возвращает одно и то же | Читаешь свой PEL, а не новые | `>` для новых, `0` — только для восстановления |
| `ERR The ID specified in XADD is equal or smaller` | Явный ID меньше последнего | `*` |

### Практика

1. Сделай поток заказов и две группы: `billing` и `notifications`; убедись, что каждая группа получает все сообщения.
2. Запусти трёх потребителей в одной группе, «убей» одного и забери его сообщения через `XAUTOCLAIM`.
3. Добавь обработку «ядовитых» сообщений: после трёх доставок перенос в поток `orders:dead` и `XACK` в основном.
4. Ограничь поток последними 10 000 записями через `MAXLEN ~` и сравни скорость с точной обрезкой.
5. Сымитируй повторную отправку производителем после тайм-аута с `IDMP` и без него.

# Модуль 6. Специальные типы: битовые карты, HyperLogLog, геоданные, Array, векторы

## 6.1 Когда обычных структур мало

| Тип | Идея | Память | Типичная задача |
|---|---|---|---|
| **Битовая карта** | Строка как массив битов, бит по номеру | 1 бит на ID: 100 млн пользователей — 12 МБ | Активность по дням, флаги, фильтры |
| **BITFIELD** | Целые числа произвольной ширины в одной строке | Сколько бит задашь | Тысячи маленьких счётчиков в одном ключе |
| **HyperLogLog** | Вероятностный подсчёт уникальных | До 12 КБ на любой объём, ошибка ~0,81% | Уникальные посетители, уникальные поисковые запросы |
| **Геоиндекс** | Сортированное множество с geohash в score | Как ZSET | «Магазины в радиусе 5 км» |
| **Array** (Redis 8.8) | Разреженный массив значений по целочисленным индексам | Только для существующих элементов | Временные ряды по номеру отсчёта, кольцевые буферы |
| **Vector Set** (Redis 8.0) | Векторы с поиском ближайших (HNSW) | Квантование уменьшает в 4–32 раза | Семантический поиск, рекомендации, кэш ответов LLM |
| **Вероятностные модули** | Bloom и Cuckoo filter, Count-Min Sketch, Top-K, t-digest | Фиксированная | «Видели ли этот email», частоты, перцентили |

## 6.3 Битовые карты и BITFIELD

- `SETBIT key offset 1` растит строку до нужного бита. Смещение — это ID: для 100 млн пользователей строка займёт 12,5 МБ. **Разреженные ID** (например, `user_id = 9 000 000 000`) создадут огромную строку — для них используют множества или HyperLogLog.
- `BITCOUNT` считает единичные биты, `BITOP AND/OR/XOR/NOT` комбинирует карты (Redis 8.2 добавил `DIFF`, `DIFF1`, `ANDOR`, `ONE`), `BITPOS` ищет первый бит.
- `BITFIELD` читает и пишет целые числа заданной ширины по смещению, с режимами переполнения `WRAP`, `SAT` (насыщение — в примере счётчик `u8` упёрся в 255) и `FAIL`.

## 6.4 HyperLogLog

Не хранит элементы — только 16 384 регистра, по которым оценивается мощность. Добавил 100 000 разных пользователей — получил оценку около 100 000 при объёме ключа ~12 КБ (в примере видно и оценку, и размер). `PFMERGE` объединяет счётчики: дни в неделю, регионы в страну. Подходит, когда допустима погрешность около 1% и не нужен список элементов.

## 6.5 Геоданные

`GEOADD key долгота широта член` — порядок именно такой: сначала долгота. Внутри это сортированное множество, где score — 52-битный geohash (`TYPE` вернёт `zset`, а `ZREM` работает для удаления). `GEOSEARCH` ищет по радиусу (`BYRADIUS`) или прямоугольнику (`BYBOX`) от точки или от члена, сортирует (`ASC`) и возвращает расстояния (`WITHDIST`) и координаты. Точность координат — около 0,6 м, поэтому `GEOPOS` возвращает чуть отличающиеся от исходных значения.

## 6.6 Array (Redis 8.8)

Новый тип от antirez: массив строк с доступом по целочисленному индексу, разреженный — пустые позиции памяти не занимают.

- `ARSET key index value ...` пишет подряд начиная с индекса, `ARGET`, `ARMGET`, `ARGETRANGE` читают; `ARLEN` — максимальный индекс + 1, `ARCOUNT` — число непустых.
- `ARSCAN` возвращает только существующие пары «индекс — значение».
- `AROP` агрегирует диапазон на сервере: `SUM`, `MIN`, `MAX`, побитовые `AND`/`OR`/`XOR`, `USED`.
- `ARINSERT` дописывает по внутреннему курсору, `ARRING key size ...` — кольцевой буфер фиксированного размера, `ARLASTITEMS` — последние вставленные.
- `ARGREP` ищет по значениям: точное совпадение, glob, регулярные выражения.

Когда брать Array, а не список: нужен доступ по номеру (номер отсчёта, номер страницы, слот времени) за O(1) и агрегаты на сервере. Тип новый, поддержка в клиентских библиотеках появляется постепенно, а в Valkey его нет.

## 6.7 Vector Set (Redis 8.0)

Тип, созданный antirez специально для векторного поиска: элементы-строки с векторами, граф HNSW для поиска ближайших.

- `VADD key VALUES dim v1 ... vN element` добавляет вектор. По умолчанию векторы квантуются до 8 бит (`Q8`), `NOQUANT` хранит float32, `BIN` — 1 бит на измерение. `REDUCE` уменьшает размерность случайной проекцией.
- `VSIM key VALUES ... | ELE element COUNT n WITHSCORES` — ближайшие по косинусной близости (1 — совпадение).
- Атрибуты в JSON (`VSETATTR`) и фильтр-выражения прямо в поиске: `FILTER ".year >= 2026 and .lang == 'en'"`.
- `VCARD`, `VDIM`, `VEMB` (получить вектор), `VREM`, `VINFO`, `VLINKS`.

Vector Set — встроенный и простой путь. Модуль поиска (модуль 19) даёт векторные индексы поверх хешей и JSON с гибридным поиском (текст + вектор + фильтры).

## 6.8 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Битовая карта весит сотни мегабайт | Большие или разреженные ID как смещения | Пересчитать ID в плотный диапазон или взять множество/HLL |
| HyperLogLog «ошибся» на маленьких числах | Вероятностная оценка | Для точных малых множеств — обычные множества |
| Геопоиск находит не то место | Перепутаны долгота и широта | `GEOADD key lon lat member` |
| Неожиданно разные результаты векторного поиска | Квантование и приближённый HNSW | `NOQUANT`, увеличить `EF`, проверить качество на своих данных |
| Клиентская библиотека не знает команд `AR*` | Новый тип Redis 8.8 | Вызывать через универсальный метод `execute_command`/`do` или обновить клиент |

# Модуль 7. Моделирование данных и именование ключей

## 7.1 Думай от запросов

В реляционной базе схему проектируют от сущностей, а запросы пишут потом. В Redis наоборот: **сначала список запросов, которые должны выполняться за O(1) или O(log N), затем структуры, которые их обслуживают**. Один и тот же факт часто хранится в нескольких структурах — это нормально, если они обновляются атомарно.

## 7.2 Именование ключей

```
<приложение>:<сущность>:<id>[:<подсущность>]
shop:user:42                 хеш профиля
shop:user:42:cart            хеш корзины
shop:user:42:orders          ZSET: заказы по времени
shop:order:1001              хеш заказа
shop:idx:orders:status:new   SET: ID новых заказов
shop:cache:product:1001      строка JSON с TTL
shop:rl:login:user42         счётчик лимита
{user:42}:cart, {user:42}:orders   hash tag — ключи одного пользователя в одном слоте кластера (модуль 15)
```

Правила: короткие, но понятные имена (каждый байт ключа хранится столько раз, сколько ключей); общий префикс приложения — для ACL и `SCAN`; ничего изменяемого и персонального (email) в имени ключа без нужды; одинаковая схема во всём коде — вынеси построение ключей в одну функцию.

## 7.3 Типовые модели

| Задача | Структуры | Запросы |
|---|---|---|
| Профиль пользователя | `HSET user:42 name ... city ...` | Поле, несколько полей, инкремент счётчика в профиле |
| Заказы пользователя по времени | `ZADD user:42:orders <ts> <order_id>` + `HSET order:<id> ...` | Последние N заказов, заказы за период |
| Вторичный индекс по статусу | `SADD idx:orders:status:new <id>` | Все новые заказы; смена статуса — `SMOVE` между множествами |
| Связь «многие ко многим» | `SADD user:42:follows 7 9`, `SADD user:7:followers 42` | Подписки, подписчики, общие — `SINTER` |
| Счётчики по времени | `INCR stats:views:2026-11-06` + `EXPIRE`, или `HINCRBY stats:views:2026-11 06 1` | Сумма за период — `MGET` или `HGETALL` |
| Лента событий | Поток или ZSET + `LTRIM`/`ZREMRANGEBYRANK` | Последние N, пагинация |
| Объект с вложенностью | JSON-тип (модуль 19) или строка с JSON | Чтение целиком или по пути |

Вторичные индексы и основные данные обновляй в одной транзакции (`MULTI`/`EXEC`) или Lua-функции, иначе после сбоя между командами индекс разойдётся с данными.

## 7.4 Пример: модель заказа

```
MULTI
HSET order:1001 user 42 status new total 1990 created 1762400000
ZADD user:42:orders 1762400000 1001
SADD idx:orders:status:new 1001
INCRBY stats:revenue:2026-11-06 1990
EXEC

# смена статуса
MULTI
HSET order:1001 status paid
SMOVE idx:orders:status:new idx:orders:status:paid 1001
EXEC
```

## 7.5 Большие ключи и горячие ключи

- **Большой ключ** — коллекция на миллионы элементов или строка на десятки мегабайт. Операции над ним блокируют сервер, удаление (`DEL`) длится заметно, репликация и миграция в кластере буксуют, а в кластере он не делится между узлами. Решение — шардирование ключа: `followers:42:0` … `followers:42:15` по хешу члена.
- **Горячий ключ** — ключ, в который идёт непропорционально много запросов: в кластере весь его трафик ложится на один узел. Решения — клиентское кэширование (модуль 8), реплики для чтения, разделение на несколько ключей с агрегацией. Найти горячие ключи помогает команда `HOTKEYS` (Redis 8.6) или `redis-cli --hotkeys` (при политике вытеснения LFU).

## 7.6 Память на ключ

Каждый ключ — это запись в словаре, объект значения и метаданные TTL: накладные расходы порядка 50–90 байт на ключ сверх данных. Десять миллионов отдельных крошечных ключей легко займут гигабайт на одни накладные расходы. Группировка в хеши (особенно маленькие, в кодировке `listpack`, и компактные хеши Redis 8.10 для объектов одной схемы) уменьшает память в разы.

## 7.7 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Индекс показывает удалённые объекты | Индекс и данные обновлялись разными командами без транзакции | `MULTI`/`EXEC` или функция |
| Один ключ на 50 млн элементов | Всё в одной коллекции | Разбиение на подключи |
| Один узел кластера перегружен | Горячий ключ | Клиентское кэширование, реплики, разделение ключа |
| Память на порядок больше данных | Миллионы мелких ключей | Группировка в хеши |
| `KEYS` для поиска объектов по признаку | Нет вторичного индекса | Множество или ZSET как индекс, либо модуль поиска |

# Модуль 8. Кэширование

## 8.1 Зачем и что кэшировать

Кэш нужен, когда чтение дорогое (тяжёлый запрос, внешний API, расчёт), а данные читают намного чаще, чем меняют. Перед внедрением ответь на три вопроса: **насколько устаревшие данные допустимы**, **что будет при пустом кэше** (холодный старт, перезапуск, вытеснение) и **как кэш узнает об изменениях**.

## 8.2 Стратегии

| Стратегия | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **Cache-aside** (ленивое заполнение) | Приложение читает кэш; при промахе — базу, затем пишет в кэш | Просто, кэшируется только нужное | Первый запрос медленный, возможна гонка при инвалидации |
| **Write-through** | При записи приложение обновляет базу и кэш | Кэш свежий | Кэшируются и никому не нужные данные; запись медленнее |
| **Write-behind** | Пишем в кэш, в базу — асинхронно | Быстрая запись | Риск потери данных; сложность |
| **Refresh-ahead** | Обновляем популярные ключи до истечения | Нет промахов на горячих ключах | Нужно знать, что популярно |

## 8.3 Кэширование в действии

```
# файл: examples/08_caching/caching.redis — вывод сценария
# Cache-aside: приложение сначала смотрит в кэш, при промахе читает базу и кладёт результат
redis> GET cache:product:1001
(nil)
# ...промах: приложение читает товар из базы и сохраняет на 10 минут
redis> SET cache:product:1001 "{\"id\":1001,\"name\":\"Mug\",\"price\":450}" EX 600
OK
redis> GET cache:product:1001
"{\"id\":1001,\"name\":\"Mug\",\"price\":450}"
redis> TTL cache:product:1001
(integer) 600

# Инвалидация при изменении данных: удалить ключ после записи в базу
redis> DEL cache:product:1001
(integer) 1

# Отрицательное кэширование: запомнить, что товара нет, на короткое время
redis> SET cache:product:9999 "__none__" EX 30
OK

# Защита от «грохочущего стада»: перестраивает кэш только тот, кто получил блокировку
redis> SET lock:cache:product:1001 worker-a NX PX 5000
OK
redis[B]> SET lock:cache:product:1001 worker-b NX PX 5000
(nil)
# worker-b не получил блокировку: ждёт немного и читает кэш снова (или отдаёт устаревшее значение)
redis> SET cache:product:1001 "{\"id\":1001,\"name\":\"Mug\",\"price\":495}" EX 600
OK
redis> DELEX lock:cache:product:1001 IFEQ worker-a
(integer) 1
redis[B]> GET cache:product:1001
"{\"id\":1001,\"name\":\"Mug\",\"price\":495}"

# Устаревшее, но быстрое значение: храним «мягкий» срок внутри значения, а «жёсткий» TTL — больше
redis> HSET cache:profile:42 data "{\"name\":\"anya\"}" soft_expire 1762400600
(integer) 2
redis> EXPIRE cache:profile:42 3600
(integer) 1
redis> HGET cache:profile:42 soft_expire
"1762400600"

# Кэш с версией: смена версии делает все старые ключи недоступными без массового удаления
redis> SET cache:version:catalog 7
OK
redis> INCR cache:version:catalog
(integer) 8
redis> SET cache:catalog:v8:page:1 "...page 1..." EX 600
OK

# Клиентское кэширование (RESP3): сервер сообщает клиенту B, что закэшированный ключ изменился
redis> SET user:42:name anya
OK
redis[B]> HELLO 3
(ответ опущен: зависит от окружения)
redis[B]> CLIENT TRACKING ON
OK
redis[B]> GET user:42:name
"anya"
# клиент B сохранил значение у себя в памяти; другой клиент меняет ключ...
redis> SET user:42:name anna
OK
# ...и B получает push-сообщение об инвалидации
(ответ клиенту B)
1) "invalidate"
2) 1) "user:42:name"
```

## 8.4 Что здесь важно

- **TTL всегда.** Кэш без срока жизни рано или поздно станет источником устаревших данных и займёт всю память. Добавляй джиттер к TTL, чтобы массово созданные ключи не истекали одновременно.
- **Инвалидация — удаление, а не обновление.** После записи в базу удаляй ключ кэша (`DEL`): следующее чтение заполнит его свежими данными. Обновление кэша вместо удаления при конкурентных записях может оставить в кэше старое значение навсегда (до TTL).
- **Отрицательное кэширование**: запомнить «такого объекта нет» на короткое время, иначе запросы несуществующих ID будут каждый раз проходить в базу — это ещё и вектор атаки.
- **«Грохочущее стадо» (cache stampede)**: популярный ключ истёк, и тысяча запросов одновременно идут в базу. Защита:
  - **блокировка на перестройку**: `SET lock:... NX PX 5000` — перестраивает только получивший блокировку, остальные ждут и перечитывают кэш или отдают устаревшее значение; снятие блокировки — только своей, через `DELEX ... IFEQ` (модуль 10);
  - **мягкий и жёсткий срок**: в значении хранится «мягкий» срок, по истечении которого один запрос обновляет данные в фоне, а остальные получают ещё действующее значение (жёсткий TTL больше);
  - **вероятностное раннее обновление** (XFetch): чем ближе истечение, тем выше вероятность, что очередной запрос обновит кэш заранее.
- **Версионирование ключей**: номер версии в имени (`cache:catalog:v8:...`) — сменил версию, и все старые ключи стали недоступны без массового удаления; их уберёт TTL.

## 8.5 Клиентское кэширование

Самый быстрый запрос к Redis — тот, которого не было. **Client-side caching** (Redis 6.0): клиент хранит значения у себя в памяти, а сервер **сам сообщает**, когда закэшированный ключ изменился.

```
клиент B ──GET user:42:name──► Redis запоминает: B читал user:42:name
клиент A ──SET user:42:name──► Redis ──push "invalidate [user:42:name]"──► клиент B удаляет из локального кэша
```

- **Режим по умолчанию** — сервер запоминает ключи, которые читал клиент (тратит память сервера). **`BCAST PREFIX cache:`** — рассылка инвалидаций по префиксу без запоминания.
- Нужен RESP3 (`HELLO 3`) для push-сообщений в том же соединении, или `REDIRECT` на отдельное соединение в RESP2.
- Современные клиенты (redis-py, Lettuce, Jedis, go-redis, node-redis) поддерживают это «из коробки» — включается опцией.
- Особенно полезно для горячих ключей: настройки, флаги функций, справочники.

## 8.6 Сессии

Сессия — хеш `session:<id>` с TTL, который продлевается на каждом запросе (`EXPIRE` или `HGETEX ... EX`). Отдельные поля (CSRF-токен, одноразовый код) — со своим сроком через `HEXPIRE` и `HSETEX`. Идентификатор сессии — криптостойкий случайный, а не ID пользователя.

## 8.7 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Пользователи видят старые данные | Нет инвалидации или TTL слишком большой | Удаление ключа после записи в базу, разумный TTL |
| База падает после перезапуска Redis | Холодный кэш, все запросы в базу | Прогрев, ограничение параллелизма, защита от лавины |
| Всплески нагрузки на базу «по часам» | Одинаковый TTL у массово созданных ключей | Джиттер в TTL |
| База перегружена запросами несуществующих ID | Нет отрицательного кэширования | Кэшировать «не найдено» на секунды |
| Кэш съел всю память | Ключи без TTL, нет `maxmemory` | TTL всегда, `maxmemory` + `allkeys-lru`/`allkeys-lfu` для чистого кэша |
| Старое значение «застряло» после конкурентной записи | Кэш обновлялся вместо удаления | Удалять ключ; при необходимости — отложенное повторное удаление |

# Модуль 9. Транзакции, WATCH, Lua и функции

## 9.1 Атомарность в Redis

Каждая команда Redis атомарна. Когда нужно выполнить несколько команд как одно целое, есть четыре инструмента:

| Инструмент | Что гарантирует | Когда |
|---|---|---|
| **`MULTI`/`EXEC`** | Команды выполняются подряд, без вклинивания других клиентов | Несколько записей, не зависящих от прочитанного |
| **`WATCH` + `MULTI`/`EXEC`** | Транзакция отменяется, если наблюдаемые ключи изменились | «Прочитал — решил — записал» на стороне клиента |
| **Условные команды Redis 8**: `SET ... IFEQ`, `DELEX`, `INCREX` | Compare-and-set одного ключа одной командой | Простые условия на одном ключе |
| **Lua: `EVAL`, функции `FCALL`** | Произвольная логика выполняется на сервере атомарно | Логика с чтением и условиями, несколько ключей |

## 9.2 Всё в действии

## 9.3 MULTI/EXEC

- После `MULTI` команды ставятся в очередь (`QUEUED`), `EXEC` выполняет их подряд, `DISCARD` отменяет очередь.
- **Отката нет.** Если команда упала при выполнении (`INCR` по строке), остальные всё равно выполнятся. Это сознательное решение: такие ошибки — баги в коде, а не ситуации, которые нужно обрабатывать в рантайме.
- **Синтаксические ошибки** обнаруживаются при постановке в очередь, и тогда `EXEC` отменяет всю транзакцию (`EXECABORT`).
- Внутри транзакции нельзя использовать результат одной команды в другой — все ответы приходят только после `EXEC`. Для логики с условиями — Lua.
- Транзакция — не пайплайн, но клиенты обычно отправляют её пайплайном: `MULTI`, команды и `EXEC` одним пакетом.

## 9.4 WATCH: оптимистичная блокировка

```
WATCH stock:mug → GET → решение в приложении → MULTI → DECRBY → EXEC
                         если между WATCH и EXEC ключ изменил кто-то другой — EXEC вернёт (nil)
```

Клиент должен **повторить** весь цикл: перечитать, пересчитать, снова `WATCH`. При высокой конкуренции за один ключ повторы становятся дорогими — тогда лучше Lua или условная команда.

## 9.5 Lua-скрипты

- Скрипт выполняется атомарно: пока он работает, сервер не обрабатывает других команд. Поэтому **скрипты должны быть короткими** — долгий скрипт остановит всех (`busy-reply-threshold`, по умолчанию 5 с, после которого другие клиенты получают `BUSY`, а скрипт можно остановить `SCRIPT KILL`, если он ещё ничего не записал).
- **Все ключи — через `KEYS[]`**, а не вычисляются внутри скрипта: иначе скрипт не будет работать в кластере, где все ключи скрипта должны лежать в одном слоте.
- `EVAL` отправляет текст скрипта каждый раз; `SCRIPT LOAD` + `EVALSHA` — только SHA1. Кэш скриптов не сохраняется при перезапуске (ошибка `NOSCRIPT` — повод отправить скрипт заново; клиенты делают это сами).
- `EVAL_RO` и `FCALL_RO` — скрипты только на чтение, их можно выполнять на репликах.
- `redis.call` выбрасывает ошибку наружу, `redis.pcall` возвращает её как значение для обработки.
- Записи скрипта реплицируются как отдельные команды (режим effects replication), поэтому недетерминированные функции внутри скрипта безопасны.

## 9.6 Функции (Redis 7.0)

Функции — следующий шаг после `EVAL`: библиотека с именем загружается командой `FUNCTION LOAD`, **хранится на сервере, попадает в RDB и AOF и реплицируется**, вызывается по имени через `FCALL`. Не нужно таскать текст скрипта в каждом приложении и обрабатывать `NOSCRIPT`.

- Первая строка библиотеки — `#!lua name=<библиотека>`, функции регистрируются через `redis.register_function`.
- Функции можно пометить флагами, например `no-writes` (тогда доступен `FCALL_RO`).
- Обновление библиотеки — `FUNCTION LOAD REPLACE`; список — `FUNCTION LIST`; резервная копия — `FUNCTION DUMP`/`RESTORE`.
- Функции и скрипты — часть кода приложения: храни их в репозитории и загружай при деплое.

## 9.7 Что выбрать

| Задача | Выбор |
|---|---|
| Несколько записей в связанные ключи | `MULTI`/`EXEC` |
| Записать, только если значение не изменилось | `SET ... IFEQ` (Redis 8.4) |
| Удалить, только если значение моё (снятие блокировки) | `DELEX ... IFEQ` (Redis 8.4) или Lua |
| Счётчик с лимитом | `INCREX` (Redis 8.8) |
| Списать остаток, только если хватает; переложить задачу из одной структуры в другую по условию | Функция или Lua |
| Сложное чтение-решение-запись с низкой конкуренцией и логикой в приложении | `WATCH` |

## 9.8 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Ожидали отката, но часть изменений применилась | В Redis нет отката | Проверять типы и данные до `EXEC`; логику с условиями — в Lua |
| `EXEC` вернул `(nil)` и данные не изменились | Сработал `WATCH` | Повторить цикл чтения и транзакции |
| `BUSY Redis is busy running a script` | Долгий скрипт | Короткие скрипты, ограничение объёма работы, `SCRIPT KILL` |
| `CROSSSLOT` при вызове скрипта в кластере | Ключи в разных слотах или вычисляются внутри скрипта | Все ключи через `KEYS[]` и hash tags |
| `NOSCRIPT No matching script` | Кэш скриптов очищен перезапуском или `SCRIPT FLUSH` | Повторить `EVAL`; лучше — функции |
| Скрипт «тормозит» сервер | Цикл по большой коллекции внутри скрипта | Ограничить объём, обрабатывать порциями |

# Модуль 10. Распределённые блокировки и ограничение частоты запросов

## 10.1 Блокировки, лимиты, семафоры — один и тот же вопрос

Все эти паттерны отвечают на вопрос «можно ли этому процессу сделать это прямо сейчас» и опираются на атомарность команд Redis. Важно понимать их **пределы**: Redis асинхронно реплицируется, процессы останавливаются на сборку мусора, часы расходятся.

## 10.2 Всё в действии

```
# файл: examples/10_locks_limits/locks_limits.redis — вывод сценария
# ===== Блокировка на одном Redis: SET NX PX + токен владельца =====
redis> SET lock:invoice:77 token-a NX PX 10000

(integer) 0
redis> DELEX lock:invoice:77 IFEQ token-a
(integer) 1

# Продление блокировки владельцем (heartbeat) — тоже только своей

if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('PEXPIRE', KEYS[1], ARGV[2])

# --- конец скрипта ---

-- KEYS[1]; ARGV: now_ms, rate_per_sec, capacity, cost
local now, rate, cap, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])

if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000))
```

## 10.3 Блокировка на одном Redis

```
получить:  SET lock:<ресурс> <уникальный токен> NX PX <ttl>      → OK — моя; (nil) — занята
продлить:  если GET == мой токен → PEXPIRE (Lua)                   — пока работа идёт
снять:     DELEX lock:<ресурс> IFEQ <мой токен>  (Redis 8.4)       — только свою
```

- **Уникальный токен** (UUID) — чтобы не снять чужую блокировку: процесс A задумался дольше TTL, блокировка истекла, её взял B, а A по завершении удаляет уже блокировку B. Сравнение и удаление должны быть **одной атомарной операцией** — `DELEX ... IFEQ` или Lua-скрипт; `GET` + `DEL` двумя командами не годится.
- **TTL обязателен**: процесс может упасть, не сняв блокировку.
- **Продление (heartbeat)** — для работы непредсказуемой длительности.
- **Ожидание** — повтор с паузой и джиттером или подписка на уведомление о снятии; не опрос в цикле без пауз.

## 10.4 Пределы: Redlock и fencing tokens

**Redlock** — алгоритм блокировки на N независимых экземплярах Redis (блокировка получена, если её удалось поставить на большинство за время меньше TTL). Мартин Клеппман в известной статье показал, что ни Redlock, ни одиночная блокировка не гарантируют взаимного исключения, если процесс-владелец может «замереть» (пауза GC, своп, сеть) дольше TTL: он проснётся и выполнит запись, думая, что блокировка его.

Практический вывод:

- **Для эффективности** (не делать одну и ту же работу дважды, не перестраивать кэш тысячей процессов) — блокировки на одном Redis достаточно: редкий дубль не страшен.
- **Для корректности** (нельзя списать деньги дважды) — нужен **fencing token**: при получении блокировки процесс получает монотонно растущий номер (`INCR fence:<ресурс>`), а хранилище данных отвергает запись с номером меньше уже виденного. Либо защищай инвариант в самой базе: уникальные ограничения, условные обновления, транзакции.
- Для сложной координации (выбор лидера, конфигурация) — системы с консенсусом: etcd, ZooKeeper, Consul.

## 10.5 Ограничение частоты

| Алгоритм | Как | Плюсы | Минусы |
|---|---|---|---|
| **Фиксированное окно** | Счётчик на окно (`rl:user42:12:00`) с TTL; `INCREX ... UBOUND N EX 60` (Redis 8.8) одной командой | Дёшево: один ключ, одна команда | На границе окон возможен двойной всплеск (N в конце минуты + N в начале следующей) |
| **Скользящий журнал** | ZSET с метками времени запросов; удалить старше окна, посчитать, добавить (Lua) | Точно | Память на каждый запрос |
| **Скользящее окно по двум счётчикам** | Текущее окно + взвешенная доля предыдущего | Почти точно и дёшево | Приближение |
| **Токен-бакет** | Хеш `tokens`, `ts`; пополнение со скоростью `rate`, ёмкость `capacity` (Lua) | Разрешает контролируемые всплески, плавная скорость | Чуть сложнее |
| **GCRA** | Одна метка «теоретического времени прибытия» | Экономно и точно | Сложнее понять |

Детали реализации: **время передавай из приложения** или бери `redis.call('TIME')` внутри скрипта; в кластере ключ лимита одного пользователя — в одном слоте; отвечай клиенту `429 Too Many Requests` с заголовком `Retry-After`.

## 10.6 Семафор

Семафор «не больше N одновременно» — ZSET держателей с метками времени: удалить просроченных (упавших), проверить количество, добавить себя — атомарно в Lua. Держатель продлевает свою метку, пока работает, и удаляет себя (`ZREM`) по завершении.

## 10.7 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Процесс снял чужую блокировку | `DEL` без проверки токена или `GET` + `DEL` | `DELEX ... IFEQ` или Lua |
| Вечная блокировка | Нет TTL или `SETNX` + `EXPIRE` | `SET ... NX PX` |
| Двойное списание при «правильной» блокировке | Пауза процесса дольше TTL | Fencing token, инварианты в базе |
| После переключения на реплику блокировку получили двое | Асинхронная репликация потеряла ключ блокировки | Блокировки — для эффективности; корректность — в базе |
| Всплеск 2N запросов на границе минуты | Фиксированное окно | Скользящее окно или токен-бакет |
| Лимиты не работают в кластере | Ключи одного лимита в разных слотах | Hash tags |

### Практика

1. Реализуй блокировку с токеном, продлением и снятием через `DELEX` и проверь, что процесс не может снять чужую блокировку.
2. Сымитируй паузу процесса дольше TTL и покажи двойное выполнение; добавь fencing token и проверку в «хранилище».
3. Сделай лимит 100 запросов в минуту на `INCREX` и на скользящем окне; сравни поведение на границе минут.

5. Ограничь число одновременных тяжёлых выгрузок семафором на 3 слота с автоматическим освобождением слотов упавших процессов.

# Модуль 11. Pub/Sub, уведомления о ключах и очереди

## 11.1 Три способа передать сообщение

| | Pub/Sub | Список (`BLMOVE`) | Поток (группы потребителей) |
|---|---|---|---|
| Доставка | Всем подписчикам, которые подключены прямо сейчас | Одному получателю | Одному потребителю в каждой группе |
| Хранение | Нет: нет подписчиков — сообщение потеряно | Да, пока не забрали | Да, пока не обрежут |
| Подтверждения и повтор | Нет | Через список «в работе» | `XACK`, PEL, `XAUTOCLAIM` |
| Гарантия | At-most-once | At-least-once (с `LMOVE`) | At-least-once |
| Для чего | Чаты, уведомления в реальном времени, инвалидация кэшей | Простые очереди задач | Очереди событий, несколько обработчиков, история |

## 11.2 В действии

```
# файл: examples/11_messaging/messaging.redis — вывод сценария

2) "news"
```

## 11.3 Pub/Sub

- `SUBSCRIBE` переводит соединение в режим подписчика: в нём можно выполнять только команды подписки и `PING` (в RESP3 ограничение снято — push-сообщения приходят в том же соединении).
- `PSUBSCRIBE` — подписка по шаблону (`news.*`); такие подписки дороже: каждое сообщение проверяется по всем шаблонам.
- `PUBLISH` возвращает число получивших. Ноль — сообщение пропало.
- **Медленный подписчик** накапливает сообщения в своём выходном буфере на сервере; при превышении `client-output-buffer-limit pubsub` (по умолчанию 32 МБ жёстко или 8 МБ в течение 60 с) сервер его отключает.
- **В кластере** обычный `PUBLISH` рассылается на все узлы — дорого при большом трафике. **Sharded Pub/Sub** (`SSUBSCRIBE`, `SPUBLISH`, Redis 7.0) привязывает канал к хеш-слоту и обрабатывает его только на узлах этого слота.

## 11.4 Уведомления о событиях ключей

`notify-keyspace-events` включает публикацию событий: `K` — канал `__keyspace@0__:<ключ>` (что случилось с ключом), `E` — канал `__keyevent@0__:<событие>` (с каким ключом случилось событие), `A` — все классы событий, `x` — истечение, `e` — вытеснение, `g` — общие (`DEL`, `EXPIRE`). Redis 8.8 добавил уведомления на уровне отдельных полей хеша.

Ограничения: это Pub/Sub — без гарантий доставки; событие истечения (`expired`) приходит, **когда ключ реально удалён** (лениво или активным циклом), а не точно в момент истечения TTL; включение уведомлений расходует CPU. Для надёжных отложенных задач используй ZSET со временем запуска, а не уведомления об истечении ключей.

## 11.5 Очереди на списках

```
производитель: LPUSH jobs <задача>
воркер:        BLMOVE jobs jobs:processing RIGHT LEFT <таймаут>   ← атомарно взял и положил в «в работе»
               ... обработка ...
               LREM jobs:processing 1 <задача>                     ← подтвердил
надзиратель:   задачи, висящие в processing дольше N минут, возвращает в jobs
```

- Блокирующие команды (`BLPOP`, `BLMOVE`, `BLMPOP`, `BZPOPMIN`, `XREAD BLOCK`) не нагружают сервер: клиент «спит» на соединении, пока не появятся данные или не истечёт тайм-аут (`0` — ждать бесконечно).
- Каждый заблокированный клиент держит соединение — учитывай это в пулах соединений клиента.
- Готовые библиотеки поверх Redis: BullMQ (Node.js), Sidekiq (Ruby), RQ, Celery и Dramatiq (Python), Asynq (Go). Они реализуют повторы, отложенные задачи, приоритеты и мониторинг.

## 11.6 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Сообщения пропадают | Pub/Sub без подписчиков или при переподключении | Поток или список, если нужна доставка |
| Подписчика отключает сервер | Переполнен выходной буфер медленного потребителя | Ускорить обработку, разгрузить через поток |
| Отложенные задачи срабатывают с опозданием или теряются | Сделаны на уведомлениях об истечении | ZSET со временем запуска и воркер |
| В кластере высокий межузловой трафик | Обычный Pub/Sub рассылается всем узлам | Sharded Pub/Sub |
| Задачи теряются при падении воркера | `BRPOP` без «в работе» | `BLMOVE` или потоки |
| Пул соединений исчерпан | Блокирующие команды держат соединения | Отдельный пул для блокирующих операций |

# Модуль 12. Память, кодировки и вытеснение

## 12.1 Куда уходит память

```
used_memory = данные (ключи + значения + структуры)
            + накладные расходы на ключи (словарь, объекты, TTL)
            + буферы клиентов (входные, выходные; Pub/Sub, реплики)
            + буфер репликации (repl-backlog), буфер AOF
            + скрипты, функции, служебные структуры
used_memory_rss = то, что видит ОС: used_memory + фрагментация аллокатора
```

`INFO memory` показывает `used_memory`, `used_memory_rss`, `mem_fragmentation_ratio`, `used_memory_peak`, `maxmemory`. `MEMORY USAGE key` — память одного ключа, `MEMORY STATS` — разбивка, `MEMORY DOCTOR` — советы.

## 12.3 Кодировки

Те же 1000 полей хеша в кодировке `hashtable` занимают больше чем вдвое больше памяти, чем в `listpack` (в примере это проверяет скрипт, чтобы вывод не зависел от точных байтов). Компактные кодировки — главный рычаг экономии памяти:

- держи коллекции маленькими там, где это естественно (разбивай большие объекты, группируй мелкие ключи в хеши);
- пороги `*-max-listpack-entries` и `*-max-listpack-value` можно поднять, если операции над коллекциями редкие, а память дорога — ценой O(N) внутри блока;
- одно длинное значение (больше `hash-max-listpack-value`, 64 байта) переводит весь хеш в `hashtable`;
- обратного перехода при уменьшении нет — только пересоздание ключа;
- компактные хеши (Redis 8.10) хранят имена полей один раз для многих ключей с одинаковой схемой.

## 12.4 maxmemory и политики вытеснения

| Политика | Кого вытесняет | Когда |
|---|---|---|
| `noeviction` (по умолчанию) | Никого: записи получают `OOM command not allowed` | Redis как хранилище: очереди, блокировки, данные, которые нельзя терять молча |
| `allkeys-lru` | Давно не читавшиеся ключи | Чистый кэш |
| `allkeys-lfu` | Редко используемые ключи (счётчик частоты с затуханием) | Кэш с явно «популярными» ключами |
| `allkeys-lrm` (Redis 8.6) | Давно не изменявшиеся ключи | Данные, ценность которых определяется свежестью записи |
| `volatile-lru`, `volatile-lfu`, `volatile-lrm`, `volatile-ttl` | Только ключи с TTL: по давности, частоте, изменению или ближайшему истечению | Смешанный экземпляр: кэш с TTL + постоянные данные |
| `allkeys-random`, `volatile-random` | Случайные | Равномерный доступ |

- LRU и LFU в Redis **приблизительные**: из выборки `maxmemory-samples` (5) ключей вытесняется лучший кандидат. Больше выборка — точнее и дороже.
- С `volatile-*` при отсутствии ключей с TTL поведение как у `noeviction` — пример показывает, что постоянный ключ уцелел, а запись всё равно получила ошибку.
- **Всегда задавай `maxmemory`** (с запасом 20–30% от памяти машины под фрагментацию, буферы и fork при сохранении), иначе Redis съест всю память и придёт OOM-killer.
- **Кэш и данные — в разных экземплярах**: тогда у каждого своя правильная политика.
- Метрики: `evicted_keys` в `INFO stats`; уведомление `evicted` в keyspace notifications.

## 12.5 Большие и горячие ключи

```bash
redis-cli --bigkeys            # самый большой ключ каждого типа (по числу элементов)
redis-cli --memkeys            # по памяти
redis-cli --hotkeys            # по частоте (нужна политика *-lfu)
HOTKEYS ...                    # Redis 8.6: отслеживание горячих ключей на сервере
MEMORY USAGE key SAMPLES 0     # точная память ключа
```

Сканирование делается через `SCAN` и безопасно для продакшена (но создаёт нагрузку — запускай на реплике).

## 12.6 Фрагментация

`mem_fragmentation_ratio = used_memory_rss / used_memory`. Около 1,0–1,5 — норма. Больше 1,5 — аллокатор держит много освободившейся, но не возвращённой памяти (после массовых удалений). Меньше 1,0 — **часть памяти в свопе**, это авария для задержек. Лечение фрагментации — активная дефрагментация (`activedefrag yes`, работает с jemalloc) или перезапуск реплики и переключение. В Redis 8 дефрагментация эффективнее и меньше влияет на задержки.

## 12.7 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| `OOM command not allowed when used memory > 'maxmemory'` | Политика `noeviction` или `volatile-*` без ключей с TTL | Больше памяти, TTL, правильная политика, разделение экземпляров |
| Данные «пропадают» без TTL | Вытеснение по `allkeys-*` в экземпляре с данными | `noeviction` для данных, отдельный экземпляр для кэша |
| OOM-killer убил Redis | Нет `maxmemory`, fork при сохранении удвоил память | `maxmemory` с запасом, `vm.overcommit_memory = 1`, отключить THP |
| `mem_fragmentation_ratio` < 1 | Своп | Убрать своп, добавить памяти |
| Память растёт без роста данных | Буферы клиентов: Pub/Sub, `MONITOR`, медленные реплики | `CLIENT LIST` (`omem`), `client-output-buffer-limit` |
| Память больше ожидаемой в разы | Миллионы мелких ключей, `hashtable` вместо `listpack` | Группировка, пороги кодировок, компактные хеши |

### Практика

1. Загрузи 1 млн пользователей отдельными ключами, хешами по одному и хешами по 100 полей; сравни `used_memory`.
2. Подбери `hash-max-listpack-entries` для своих данных и измерь компромисс память/скорость с `redis-benchmark`.
3. Настрой экземпляр-кэш с `maxmemory 100mb` и `allkeys-lfu`, заполни его и посмотри на `evicted_keys`.
4. Найди большие ключи в учебной базе через `--bigkeys` и `--memkeys`.
5. Удали половину ключей и посмотри, как меняются `used_memory`, `used_memory_rss` и фрагментация; включи `activedefrag`.

# Модуль 13. Персистентность: RDB и AOF

## 13.1 Зачем Redis пишет на диск

Данные живут в памяти, а диск нужен, чтобы пережить перезапуск и сбой. Два механизма:

| | RDB (снимок) | AOF (журнал команд) |
|---|---|---|
| Что пишется | Компактный бинарный снимок всех данных на момент времени | Каждая команда записи |
| Как часто | По расписанию (`save 3600 1 300 100 60 10000`) или командой `BGSAVE` | Постоянно; сброс на диск по `appendfsync` |
| Потери при сбое | Всё после последнего снимка — минуты | `everysec` — до ~1 с; `always` — ничего, но медленно |
| Скорость восстановления | Быстро | Медленнее (с RDB-преамбулой — почти как RDB) |
| Размер | Маленький | Больше; периодически переписывается |
| Для чего | Бэкапы, быстрый старт, перенос данных | Минимальные потери данных |

## 13.2 Как работает снимок: fork и copy-on-write

```
основной процесс ──fork()──► дочерний процесс пишет RDB из «замороженной» копии памяти
       │                         (страницы общие, пока их никто не меняет)
       └── продолжает принимать записи: изменённая страница копируется (copy-on-write)
```

Следствия:

- `BGSAVE` не блокирует запросы, но **сам `fork()` на инстансе в десятки гигабайт занимает заметное время** (копирование таблиц страниц) — пик задержки виден в `latest_fork_usec` в `INFO stats`.
- **Во время сохранения память может вырасти до двух раз** при интенсивной записи (каждая изменённая страница копируется). Отсюда правило запаса памяти и `vm.overcommit_memory = 1` (иначе `fork` может не выполниться: `Can't save in background: fork: Cannot allocate memory`).
- **Transparent Huge Pages** нужно отключить: с ними copy-on-write копирует страницы по 2 МБ вместо 4 КБ, и задержки растут.
- `SAVE` (без `BG`) блокирует сервер полностью — не используй на рабочем экземпляре.

## 13.3 AOF

```ini
appendonly yes
appendfsync everysec          # always | everysec | no
aof-use-rdb-preamble yes      # базовый файл AOF в формате RDB + инкрементальные команды
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

- **`appendfsync everysec`** — разумный выбор по умолчанию: потеря до секунды записей при сбое машины (при падении только процесса Redis данные уже в буфере ОС и не теряются).
- **Перезапись AOF** (`BGREWRITEAOF`, автоматически по росту) строит компактный файл из текущего состояния. С Redis 7.0 **multi-part AOF**: каталог `appendonlydir` с базовым файлом, инкрементальными файлами и манифестом — перезапись больше не требует двойной записи в старый и новый файл.
- **`WAITAOF numlocal numreplicas timeout`** (Redis 7.2) — дождаться, пока запись попадёт в AOF на диске локально и на репликах: синхронная надёжность для отдельных критичных операций.
- **`BACKUP`** (Redis 8.10) — серверная реализация резервного копирования и восстановления на основе multi-part AOF.
- Повреждённый хвост AOF после сбоя чинит `redis-check-aof --fix`; RDB проверяет `redis-check-rdb`.

## 13.4 Что выбрать

| Сценарий | Настройка |
|---|---|
| Чистый кэш, данные легко восстановить | Без персистентности (`save ""`, `appendonly no`) или редкие RDB для быстрого прогрева |
| Сессии, лимиты, очереди — потеря минуты неприятна, но терпима | RDB каждые несколько минут |
| Очереди, данные, потеря больше секунды недопустима | AOF `everysec` + RDB-преамбула (по умолчанию в новых версиях) + реплика |
| Отдельные критичные записи | `WAITAOF` после записи |
| Бэкапы | RDB-файлы по расписанию (`BGSAVE`, копия `dump.rdb`) во внешнее хранилище, с проверкой восстановления |

**Персистентность — не замена репликации, а репликация — не замена бэкапу:** удалённые по ошибке данные (`FLUSHALL`) мгновенно уйдут на реплики и в AOF. `FLUSHALL` и `FLUSHDB` стоит запретить через ACL для приложений, а бэкапы хранить вне сервера.

## 13.5 Восстановление

1. Остановить Redis.
2. Положить `dump.rdb` (или каталог `appendonlydir`) в `dir` из конфигурации.
3. Если включён AOF — Redis при старте читает **AOF, а не RDB**. Для восстановления из RDB временно выключи `appendonly`, запусти, затем включи AOF через `CONFIG SET appendonly yes` (Redis построит AOF из текущих данных) и сохрани конфигурацию.
4. Проверить `DBSIZE`, выборочно — ключи, `INFO persistence` (`loading`, `rdb_last_load_keys_loaded`).

## 13.6 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| После перезапуска все данные пропали | Персистентность выключена или файл в непостоянном томе контейнера | RDB/AOF, том для `/data` |
| `MISCONF Redis is configured to save RDB snapshots, but it's currently unable to persist to disk` | Не удался `BGSAVE` (место, права, fork) — Redis запрещает запись | Починить диск или память; не отключать `stop-writes-on-bgsave-error` вслепую |
| `Can't save in background: fork: Cannot allocate memory` | `vm.overcommit_memory = 0` и мало свободной памяти | `vm.overcommit_memory = 1`, запас памяти |
| Пики задержки раз в несколько минут | `fork` большого инстанса, THP | Отключить THP, сохранять на реплике, меньше инстанс |
| Восстановили RDB, а Redis загрузил пустой AOF | При включённом AOF загружается AOF | Порядок восстановления из 13.5 |
| `FLUSHALL` уничтожил данные везде | Ошибка оператора реплицировалась | ACL, внешние бэкапы |

### Практика

1. Запусти Redis в Docker с томом и AOF, запиши данные, убей контейнер `docker kill` и проверь, что потеряно.
2. Сравни время старта на 1 млн ключей с RDB, с AOF без преамбулы и с RDB-преамбулой.

4. Восстанови базу из `dump.rdb` в новом контейнере с включённым AOF по шагам из 13.5.
5. Выполни запись с `WAITAOF 1 0 100` и объясни ответ.

# Модуль 14. Репликация и Sentinel

## 14.1 Репликация

```
           записи
 клиенты ─────────► master ── поток команд (асинхронно) ──► replica 1 (только чтение)
                      │                                └──► replica 2
                      └ repl-backlog: кольцевой буфер последних команд для догоняющих реплик
```

```ini
# на реплике
replicaof 10.0.0.10 6379
masterauth <пароль пользователя репликации>
replica-read-only yes
```

- **Полная синхронизация**: мастер делает RDB (`fork`) и отправляет его реплике, затем поток команд. С `repl-diskless-sync yes` (по умолчанию) снимок идёт прямо в сокет, без записи на диск.
- **Частичная синхронизация** (`PSYNC`): после кратковременного обрыва реплика догоняет из `repl-backlog`, если пропущенное ещё в буфере. Слишком маленький буфер (по умолчанию 1 МБ) — и каждый обрыв превращается в полную синхронизацию с `fork` на мастере. На нагруженных системах ставят сотни мегабайт.
- **Репликация асинхронная.** Подтверждённая клиенту запись может не дойти до реплики, если мастер упал. `WAIT numreplicas timeout` блокирует клиента, пока запись не подтвердят N реплик, — уменьшает окно потерь, но не делает систему строго консистентной.
- **Чтение с реплик** разгружает мастер, но данные могут отставать на миллисекунды и больше: «записал и сразу прочитал с реплики» может вернуть старое значение.
- **Отставание**: `INFO replication` на мастере (`slave0: ... offset=..., lag=...`) и на реплике (`master_repl_offset`, `master_last_io_seconds_ago`).
- **Защита от записи в одиночку**: `min-replicas-to-write 1` + `min-replicas-max-lag 10` — мастер отказывает в записи, если у него нет хотя бы одной свежей реплики (снижает потери при split brain).

## 14.2 Sentinel: автоматическое переключение

```
 sentinel-1   sentinel-2   sentinel-3        ← наблюдают, договариваются кворумом
      │            │            │
      ▼            ▼            ▼
   master  ◄──── replica-1, replica-2
 мастер недоступен для кворума Sentinel'ов → выбирается лидер-Sentinel →
 лучшая реплика становится мастером (REPLICAOF NO ONE) → остальные перенастраиваются →
 клиенты узнают новый адрес у Sentinel
```

```ini
# sentinel.conf
sentinel monitor mymaster 10.0.0.10 6379 2      # кворум 2 из 3
sentinel auth-user mymaster sentinel-user
sentinel auth-pass mymaster <пароль>
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
```

- **Минимум три Sentinel** на независимых машинах (или в разных зонах доступности), нечётное число. Два Sentinel не дадут кворума при падении одного.
- **Клиенты подключаются через Sentinel**: спрашивают `SENTINEL get-master-addr-by-name mymaster` и подписываются на события переключения. Все основные клиентские библиотеки это поддерживают.
- **Потеря данных при переключении** возможна: записи, не успевшие дойти до новой реплики, пропадут. Это цена асинхронной репликации.
- **Split brain**: старый мастер, отрезанный от сети вместе с частью клиентов, продолжает принимать записи, которые потом будут потеряны. Ограничивается `min-replicas-to-write`.
- **Тестируй переключение**: `SENTINEL FAILOVER mymaster` на стенде, с нагрузкой, и проверь, как ведут себя клиенты.

## 14.3 Реплика как инструмент эксплуатации

- **Бэкапы и сохранение на реплике**: `fork` и RDB не трогают мастер.
- **Обновление версии без простоя**: обновить реплики → переключиться → обновить старый мастер.
- **Аналитика и тяжёлые чтения** (`SCAN`, `--bigkeys`) — на реплике.
- **Реплика реплики** (каскад) снижает нагрузку на мастер при многих репликах.

## 14.4 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Реплика постоянно делает полную синхронизацию | Маленький `repl-backlog-size`, длинные обрывы, переполнение буфера реплики на мастере | Увеличить backlog и `client-output-buffer-limit replica` |
| После переключения пропали последние записи | Асинхронная репликация | `WAIT`/`WAITAOF` для критичных записей; база данных для того, что нельзя терять |
| Sentinel не переключает | Нет кворума, Sentinel'ы на одной машине с мастером | Три и больше Sentinel на разных машинах |
| Два мастера после сетевого разделения | Split brain | `min-replicas-to-write`, проверка топологии |
| «Записал, прочитал старое» | Чтение с реплики | Читать свои записи с мастера |
| Клиенты не видят новый мастер | Клиент подключён напрямую к IP, а не через Sentinel | Клиентская поддержка Sentinel или прокси |

### Практика

1. Подними в Docker Compose мастер и две реплики, убедись, что реплики только на чтение, и посмотри `INFO replication`.
2. Добавь три Sentinel, останови мастер-контейнер и проследи за переключением в логах Sentinel.
3. Под нагрузкой записи сделай переключение и посчитай потерянные записи; затем используй `WAIT 1 100` и сравни.
4. Уменьши `repl-backlog-size` до 16 КБ, разорви связь реплики на 10 секунд и посмотри, какая синхронизация произошла.
5. Настрой клиентскую библиотеку своего языка на работу через Sentinel и проверь переподключение при переключении.

# Модуль 15. Redis Cluster

## 15.1 Зачем кластер

Один Redis упирается в память одной машины и в одно ядро для выполнения команд. **Redis Cluster** распределяет ключи по нескольким мастерам (шардам), у каждого — свои реплики, и сам выполняет переключение без Sentinel.

```
16 384 хеш-слота:  slot = CRC16(ключ) mod 16384

 master A: слоты 0–5460       ← replica A'
 master B: слоты 5461–10922   ← replica B'
 master C: слоты 10923–16383  ← replica C'
 узлы общаются по шине кластера (порт +10000): пинги, состояние, голосование при переключении
```

## 15.2 Как клиент находит ключ

```
клиент ──GET user:42──► узел A
узел A: слот 8562 не мой ──► -MOVED 8562 10.0.0.12:6379
клиент обновляет карту слотов и идёт на узел B (умные клиенты кэшируют карту: CLUSTER SHARDS)
во время миграции слота: -ASK 8562 10.0.0.13:6379 → клиент отправляет ASKING и команду на новый узел
```

Все основные клиентские библиотеки поддерживают кластер: держат карту слотов и обрабатывают `MOVED` и `ASK` сами.

## 15.3 Ограничения: всё про слоты

Команды над несколькими ключами (`MGET`, `MSET`, `SUNION`, `RENAME`, транзакции, Lua-скрипты, функции) работают, **только если все ключи в одном слоте**. Иначе — ошибка `CROSSSLOT Keys in request don't hash to the same slot`.

**Hash tags**: если в имени ключа есть `{...}`, слот вычисляется только по содержимому скобок:

```
CLUSTER KEYSLOT user:42:cart          → один слот
CLUSTER KEYSLOT user:42:orders        → другой слот
CLUSTER KEYSLOT {user:42}:cart        → слот от "user:42"
CLUSTER KEYSLOT {user:42}:orders      → тот же слот — можно MULTI, Lua, SUNION
```

Ловушка hash tags — **перекос**: если всё помечено `{tenant}` одного крупного клиента, весь его трафик ляжет на один шард. Выбирай тег с высокой кардинальностью (пользователь, заказ), а не с низкой (страна, тип).

Другие ограничения: только база 0; `KEYS` и `SCAN` работают на каждом узле отдельно (обход — по всем мастерам); обычный Pub/Sub рассылается на все узлы (используй sharded Pub/Sub).

## 15.4 Создание и управление

```bash
# 6 узлов: 3 мастера + 3 реплики
redis-cli --cluster create 10.0.0.11:6379 10.0.0.12:6379 10.0.0.13:6379 \
          10.0.0.14:6379 10.0.0.15:6379 10.0.0.16:6379 --cluster-replicas 1

redis-cli -c -h 10.0.0.11                    # -c: следовать MOVED/ASK
CLUSTER SHARDS                               # топология (заменяет устаревший CLUSTER SLOTS)
CLUSTER INFO                                 # cluster_state:ok, число известных узлов
redis-cli --cluster check 10.0.0.11:6379
redis-cli --cluster add-node new:6379 10.0.0.11:6379
redis-cli --cluster rebalance 10.0.0.11:6379
redis-cli --cluster reshard 10.0.0.11:6379
CLUSTER FAILOVER                             # на реплике: плановое переключение
```

```ini
cluster-enabled yes
cluster-config-file nodes.conf
cluster-node-timeout 15000
cluster-require-full-coverage yes   # no — обслуживать доступные слоты, даже если часть недоступна
cluster-allow-reads-when-down no
```

- **Решардинг** переносит слоты между узлами без остановки. В Redis 8 появилась **атомарная миграция слотов** на стороне сервера, а с 8.10 `redis-cli --cluster reshard` и `rebalance` используют её: слот переносится целиком, без долгого режима `ASK` по ключам.
- **Переключение**: если мастер недоступен для большинства мастеров дольше `cluster-node-timeout`, его реплика выбирается новым мастером. Без реплик падение мастера делает его слоты недоступными.
- **Большие ключи** не делятся между шардами и замедляют миграцию.

## 15.5 Cluster, Sentinel или один экземпляр

| Ситуация | Выбор |
|---|---|
| Данные помещаются в память одной машины, нагрузка — в одно ядро | Один мастер + реплики + Sentinel (проще, полный набор мультиключевых операций) |
| Данных больше, чем памяти одной машины, или упираемся в CPU на запись | Cluster |
| Нужна только масштабируемость чтения | Реплики |
| Не хочется эксплуатировать | Managed-сервис с кластерным режимом |

## 15.6 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| `CROSSSLOT Keys in request don't hash to the same slot` | Мультиключевая операция по разным слотам | Hash tags, разбиение операции |
| `MOVED` в ответе приложению | Клиент без поддержки кластера или `redis-cli` без `-c` | Кластерный клиент |
| Один шард перегружен | Перекос hash tags или горячий ключ | Тег с высокой кардинальностью, клиентское кэширование |
| `CLUSTERDOWN The cluster is down` | Слоты без живого мастера | Реплики у каждого мастера; `cluster-require-full-coverage` по ситуации |
| Lua-скрипт работает в одиночном Redis и падает в кластере | Ключи вычисляются в скрипте или в разных слотах | Ключи через `KEYS[]` с общим hash tag |
| Обход ключей нашёл не всё | `SCAN` только на одном узле | Обходить все мастера |

### Практика

1. Подними кластер из 6 узлов в Docker Compose (или `create-cluster` из исходников Redis) и создай 100 000 ключей.
2. Выполни `MSET` двух ключей без hash tag и с ним; посмотри на ошибку и на `CLUSTER KEYSLOT`.
3. Добавь седьмой и восьмой узлы и перебалансируй слоты под нагрузкой `redis-benchmark --cluster`.
4. Останови мастер и проследи, как его реплика становится мастером и что видят клиенты.
5. Спроектируй ключи корзины и заказов пользователя так, чтобы оформление заказа выполнялось одним Lua-скриптом в кластере.

# Модуль 16. Безопасность: ACL, TLS и защищённая конфигурация

## 16.1 Модель угроз

Redis выполняет любую команду любого подключившегося клиента: `FLUSHALL`, `CONFIG SET dir`, `EVAL`, `MODULE LOAD`. Открытый в интернет Redis без пароля — классика взломов: данные стирают, а через запись файлов конфигурации и модулей получают выполнение кода на сервере. В 2025–2026 годах в Redis исправили серию уязвимостей, ведущих к удалённому выполнению кода через Lua, `RESTORE` и загрузку повреждённых данных, — **своевременное обновление минорных версий** обязательно.

## 16.2 ACL в действии


## 16.3 ACL

```
ACL SETUSER <имя> on|off  >пароль  #sha256-хеш
                  ~шаблон-ключей  %R~только-чтение  %W~только-запись  allkeys
                  &шаблон-каналов  allchannels
                  +команда  -команда  +@категория  -@категория  allcommands
                  (селектор: дополнительный набор правил)
```

- **Категории**: `@read`, `@write`, `@admin`, `@dangerous` (`FLUSHALL`, `KEYS`, `CONFIG`, `DEBUG`, `SHUTDOWN` и другие), `@keyspace`, `@string`, `@hash`, `@pubsub`, `@scripting`, `@slow`, `@fast`. Список команд категории — `ACL CAT <категория>`.
- **Минимальные права**: приложение — свой префикс ключей, `+@read +@write -@dangerous`; аналитик — `+@read`; кэш-сервис — несколько конкретных команд.
- **Права на ключи по типу доступа** (Redis 7.0): `%R~` — только чтение ключей, `%W~` — только запись.
- **Селекторы** (`(~logs:* +xadd)`) — дополнительные наборы правил у одного пользователя.
- **`ACL DRYRUN`** проверяет, разрешена ли команда пользователю, без выполнения. **`ACL LOG`** показывает отказы: кто, какую команду, по какому ключу — первое, куда смотреть при подозрительной активности.
- **Пользователь `default`** используется клиентами без `AUTH` (и старым `requirepass`). Задай ему пароль или выключи (`ACL SETUSER default off`) и заведи именованных пользователей.
- **Хранение**: `aclfile /etc/redis/users.acl` + `ACL SAVE`/`ACL LOAD` — или пользователи прямо в `redis.conf`. В файле хранятся SHA-256 хеши паролей.
- **Пользователи для служебных задач**: отдельные для репликации (`masterauth`/`masteruser`), Sentinel, экспортера метрик (`+info +ping +client|list ...`).

## 16.4 Защищённая конфигурация

```ini
bind 10.0.0.10 127.0.0.1                 # только внутренние интерфейсы
protected-mode yes                        # отказ внешним подключениям, если нет пароля
port 0                                    # отключить нешифрованный порт...
tls-port 6379                             # ...и слушать только TLS
tls-cert-file /etc/redis/tls/redis.crt
tls-key-file /etc/redis/tls/redis.key
tls-ca-cert-file /etc/redis/tls/ca.crt
tls-auth-clients optional                 # yes — обязательные клиентские сертификаты (mTLS)
tls-replication yes
tls-cluster yes
aclfile /etc/redis/users.acl
enable-debug-command no                   # (по умолчанию) DEBUG недоступен
enable-module-command no                  # MODULE LOAD недоступен в рантайме
enable-protected-configs no               # CONFIG SET dir/dbfilename запрещены
rename-command FLUSHALL ""                # устаревший способ; используй ACL
```

- **Сеть**: Redis никогда не смотрит в интернет; доступ — из приватной сети, через группы безопасности и сетевые политики Kubernetes.
- **TLS** — для трафика между зонами, клиентами вне доверенной сети, по требованиям безопасности. Redis 8.6 добавил автоматическую аутентификацию клиента по сертификату, а 8.10 — аутентификацию узлов между собой по сертификатам.
- **Не запускай Redis от root** и ограничь права на каталог данных.
- **Обновляй минорные версии** сразу после выхода исправлений безопасности: в release notes они помечены `SECURITY`.

## 16.5 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Данные стёрты, в базе ключ с требованием выкупа | Redis доступен из интернета без пароля | Закрыть сеть, ACL, проверить сервер на компрометацию |
| Приложение может выполнить `FLUSHALL` и `KEYS` | Работает под `default` со всеми правами | Отдельный пользователь с минимальными правами |
| `NOPERM` после деплоя | Новая команда или префикс ключей не разрешены | Обновить ACL вместе с кодом, `ACL DRYRUN` в тестах |
| `WRONGPASS invalid username-password pair` | Неверный пароль или пользователь выключен | `ACL GETUSER`, ротация паролей без простоя (у пользователя может быть несколько паролей) |
| Пароль виден в списке процессов | `redis-cli -a` | `REDISCLI_AUTH` или файл конфигурации клиента |
| Уязвимость в старой версии | Нет регулярных обновлений | Процесс обновления минорных версий |

### Практика

1. Заведи пользователей для приложения, аналитика, экспортера метрик и репликации с минимальными правами и проверь их через `ACL DRYRUN`.

4. Проведи ротацию пароля без простоя: добавь второй пароль, переключи приложение, удали старый (`<старый`).
5. Посмотри `ACL LOG` после серии запрещённых команд и придумай алерт на его рост.

# Модуль 17. Производительность и масштабирование

## 17.1 Почему Redis быстрый и что его замедляет

```
клиенты ──сеть──► I/O-потоки (чтение и разбор запросов, запись ответов; io-threads)
                        │
                        ▼
                  основной поток: выполняет команды строго по одной   ← здесь узкое место
                        │
                  фоновые потоки: освобождение памяти (UNLINK), fsync AOF, закрытие файлов
                  дочерние процессы: BGSAVE, перезапись AOF
```

Redis быстр, потому что данные в памяти, структуры эффективные, а выполнение однопоточное — без блокировок. Отсюда главное правило: **время одной команды умножается на всех ожидающих клиентов**. Одна команда на 100 мс — и все остальные клиенты ждут 100 мс.

## 17.2 Источники задержек

| Источник | Пример | Что делать |
|---|---|---|
| **Медленные команды O(N)** | `KEYS *`, `HGETALL`/`SMEMBERS`/`LRANGE 0 -1` на больших коллекциях, `SORT`, `ZUNIONSTORE` больших множеств, `FLUSHALL` | `SCAN`-семейство, пагинация, ограничение размеров, `FLUSHALL ASYNC` |
| **Большие ключи** | Удаление списка на 10 млн элементов через `DEL` | `UNLINK`, `lazyfree-lazy-*`, разбиение ключей |
| **Долгие Lua-скрипты** | Цикл по коллекции внутри скрипта | Короткие скрипты, обработка порциями |
| **Сеть и число запросов** | 1000 отдельных `GET` на страницу | Пайплайн, `MGET`, клиентское кэширование |
| **Fork** | `BGSAVE`/перезапись AOF на инстансе 50 ГБ | Меньше инстансы, сохранение на реплике, отключить THP |
| **Своп** | `mem_fragmentation_ratio` < 1 | Отключить своп для Redis, запас памяти |
| **Истечение множества ключей разом** | Миллион ключей с одинаковым TTL | Джиттер в TTL |
| **Соединения** | Новое соединение на каждый запрос, тысячи соединений | Пул соединений в клиенте |

## 17.3 Пайплайн

Без пайплайна каждая команда — полный сетевой круг (RTT). Пайплайн отправляет пачку команд, не дожидаясь ответов:

```
без пайплайна:  GET a →  ← ответ   GET b →  ← ответ   ...     1000 команд × 0,5 мс RTT = 500 мс
с пайплайном:   GET a, GET b, ... GET z →   ← все ответы       ≈ 1 RTT + время выполнения
```

Пайплайн не атомарен (между командами могут вклиниться другие клиенты) — для атомарности транзакция или Lua. Разумный размер пачки — сотни или тысячи команд, чтобы не раздувать буферы.

## 17.4 Многопоточный ввод-вывод

`io-threads N` выносит чтение, разбор запросов и запись ответов в отдельные потоки, а выполнение команд остаётся в основном потоке. Помогает при больших объёмах трафика и множестве клиентов на машинах с несколькими ядрами; в Redis 8 реализация заметно улучшена. Ставь `io-threads` меньше числа ядер (например, 4 на 8-ядерной машине) и измеряй — на слабой нагрузке выигрыша нет.

## 17.5 Измерение

```bash
redis-benchmark -t set,get -n 1000000 -c 50 -P 16 -q      # -P: пайплайн
redis-benchmark -t set -d 1024 -n 200000 -q                 # размер значения 1 КБ
redis-cli --latency -h host                                 # задержка до сервера
redis-cli --latency-history -i 5                            # история задержки
redis-cli --latency-dist                                    # распределение
redis-cli --intrinsic-latency 30                            # собственная задержка машины (запускать на сервере)
```

`redis-benchmark` измеряет сервер в идеальных условиях; реальная картина — по метрикам приложения (p99 времени запросов к Redis) и по `LATENCY` и `SLOWLOG` (модуль 18).

## 17.6 Масштабирование

| Узкое место | Решение |
|---|---|
| Чтения | Реплики, клиентское кэширование |
| Память | Компактные структуры, вытеснение, Cluster |
| CPU на запись | Cluster (шардирование), разнести разные задачи по разным экземплярам |
| Сеть | Пайплайны, `MGET`, сжатие больших значений в приложении |
| Горячий ключ | Клиентское кэширование, копии ключа с агрегацией |

**Разные задачи — разные экземпляры**: кэш (`allkeys-lfu`, без персистентности), очереди и данные (`noeviction`, AOF), сессии. Так они не мешают друг другу настройками, вытеснением и задержками.

## 17.7 Настройки ОС

- `vm.overcommit_memory = 1` — чтобы `fork` не падал.
- Отключить Transparent Huge Pages: `echo never > /sys/kernel/mm/transparent_hugepage/enabled`.
- `net.core.somaxconn` и `tcp-backlog` — для большого числа подключений.
- Не использовать своп для Redis; держать запас памяти.
- В контейнерах — лимит памяти больше `maxmemory` с запасом на буферы и fork.

## 17.8 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Периодические зависания на десятки миллисекунд | `KEYS`, `HGETALL` больших хешей, удаление больших ключей | `SLOWLOG`, `SCAN`, `UNLINK` |
| Высокая задержка при низкой загрузке CPU Redis | Много мелких запросов, RTT | Пайплайн, `MGET` |
| Пики задержки раз в N минут | `fork` при `BGSAVE` | Сохранение на реплике, отключить THP, меньше инстанс |
| CPU основного потока 100% | Нагрузка упёрлась в одно ядро | Оптимизировать команды, `io-threads`, шардирование |
| Тысячи соединений | Нет пула, соединение на запрос | Пул соединений, мультиплексирование в клиенте |
| Задержка «прыгает» под нагрузкой на одном узле кластера | Горячий ключ | Клиентское кэширование, разделение ключа |

### Практика

1. Измерь `redis-benchmark` для `SET`/`GET` без пайплайна и с `-P 16` и `-P 128`.
2. Запусти `KEYS *` на 5 млн ключей и одновременно `redis-cli --latency-history` в другом окне.
3. Перепиши загрузку 100 000 ключей из цикла `SET` на пайплайн и сравни время в своём языке.
4. Включи `io-threads 4` на многоядерной машине и сравни пропускную способность под 200 клиентами.
5. Проверь настройки `overcommit_memory` и THP на своём сервере и посмотри предупреждения в логе Redis при старте.

# Модуль 18. Мониторинг и диагностика

## 18.1 INFO — главный источник метрик

```
INFO server        версия, uptime, режим (standalone/cluster), io_threads_active
INFO clients       connected_clients, blocked_clients, maxclients
INFO memory        used_memory, used_memory_rss, mem_fragmentation_ratio, maxmemory, maxmemory_policy
INFO persistence   rdb_last_bgsave_status, aof_last_write_status, rdb_changes_since_last_save
INFO stats         instantaneous_ops_per_sec, keyspace_hits/misses, expired_keys, evicted_keys,
                   rejected_connections, latest_fork_usec, total_net_input/output_bytes
INFO replication   role, connected_slaves, master_link_status, offset и lag реплик
INFO cpu           used_cpu_sys/user, для основного и фоновых потоков
INFO commandstats  число вызовов, суммарное и среднее время по каждой команде
INFO errorstats    ошибки по типам: WRONGTYPE, OOM, NOPERM...
INFO keyspace      число ключей и ключей с TTL по базам
```

**Доля попаданий кэша** = `keyspace_hits / (keyspace_hits + keyspace_misses)`. **`commandstats`** быстро показывает, какие команды съедают время (`usec_per_call`) — первым делом смотри туда при росте CPU.

## 18.2 SLOWLOG

```
CONFIG SET slowlog-log-slower-than 10000    # микросекунды; 10 мс по умолчанию
CONFIG SET slowlog-max-len 1024
SLOWLOG GET 10        # id, время, длительность (мкс), команда с аргументами, клиент
SLOWLOG LEN
SLOWLOG RESET
```

Важно: SLOWLOG считает **только время выполнения** на сервере, без сети и ожидания в очереди. Команда может выполняться 1 мс, а клиент ждать 100 мс из-за другой медленной команды перед ней. Redis 8.8 добавил ограничения на размер записи (`slowlog-entry-max-argc`, `slowlog-entry-max-string-len`), а 8.10 — общее число аргументов в ответе `SLOWLOG GET`.

## 18.3 LATENCY и MEMORY DOCTOR

```
CONFIG SET latency-monitor-threshold 100    # мс; события дольше порога записываются
LATENCY LATEST           # последние пики по типам событий: command, fork, expire-cycle, aof-fsync...
LATENCY HISTORY fork
LATENCY DOCTOR           # отчёт с объяснениями и советами человеческим языком
LATENCY HISTOGRAM GET SET    # распределение задержек команд (Redis 7.0)
MEMORY DOCTOR
```

## 18.4 Клиенты

```
CLIENT LIST           # id, addr, name, age, idle, flags, db, cmd, qbuf, omem, tot-mem...
CLIENT INFO           # о текущем соединении
CLIENT SETNAME api-worker-3     # называй соединения — сильно упрощает разбор
CLIENT KILL ID 1234
CLIENT NO-EVICT on    # служебному соединению не грозит отключение при нехватке памяти
```

Большой `omem` (выходной буфер) — медленный потребитель, подписчик Pub/Sub или `MONITOR`. Большой `qbuf` — клиент шлёт огромные команды. `idle` в часах — утечка соединений в пуле.

**`MONITOR`** выводит все команды в реальном времени, но снижает производительность сервера в разы и раздувает буфер — только на минуту, на стенде или реплике, никогда как постоянный инструмент.

## 18.5 Метрики и алерты

Стек: **redis_exporter** (Prometheus) → Grafana, либо Redis Insight, Datadog, облачный мониторинг. Обязательные алерты:

| Алерт | Порог (ориентир) |
|---|---|
| Экземпляр недоступен, `master_link_status:down` на реплике | Любое |
| Память близко к `maxmemory` | > 85% |
| Рост `evicted_keys` там, где вытеснения быть не должно | Любой рост |
| `rejected_connections`, `connected_clients` близко к `maxclients` | Рост, > 80% |
| `mem_fragmentation_ratio` | < 1 (своп) или > 1,5 надолго |
| `rdb_last_bgsave_status` или `aof_last_write_status` не `ok` | Любое |
| Отставание реплик | Растущий lag |
| Доля попаданий кэша | Резкое падение |
| `blocked_clients` | Неожиданный рост |
| Задержка p99 со стороны приложения | По SLO |

## 18.6 Разбор инцидента «Redis тормозит»

1. **Со стороны Redis или сети?** `redis-cli --latency` с машины приложения и с самой машины Redis.
2. **`SLOWLOG GET`** и **`INFO commandstats`**: есть ли медленные команды, какие команды стали дороже.
3. **`LATENCY DOCTOR`**: fork, истечение ключей, fsync AOF.
4. **`INFO memory`**: своп, фрагментация, близость к `maxmemory` (вытеснение тоже стоит времени).
5. **`CLIENT LIST`**: всплеск соединений, огромные буферы, `MONITOR`.
6. **CPU основного потока**: упёрся в 100% — смотри, что за команды; нужна оптимизация или шардирование.
7. **Что изменилось**: деплой, новый тип запросов, рост данных, большой ключ, массовое истечение.

## 18.7 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| SLOWLOG пуст, а клиенты ждут | Задержка в сети или очереди за другой командой | `--latency`, `LATENCY`, метрики клиента |
| `MONITOR` «положил» сервер | Огромный выходной буфер и накладные расходы | Только кратко и на стенде |
| Мониторинг не заметил вытеснение | Нет алерта на `evicted_keys` | Алерты из 18.5 |
| Непонятно, какой сервис создаёт нагрузку | Соединения без имён | `CLIENT SETNAME`, отдельные пользователи ACL |
| Не видно, что кэш перестал работать | Нет метрики доли попаданий | `keyspace_hits/misses` в дашборде |

# Модуль 19. Поиск, JSON, временные ряды и AI в Redis Open Source 8

## 19.1 Что входит в Redis Open Source 8

Начиная с Redis 8.0 возможности, которые раньше были отдельными модулями Redis Stack, входят в Redis Open Source (официальный Docker-образ и пакеты):

| Возможность | Команды | Для чего |
|---|---|---|
| **Redis Query Engine** (поиск) | `FT.CREATE`, `FT.SEARCH`, `FT.AGGREGATE`, `FT.HYBRID` | Вторичные индексы, полнотекстовый поиск, фильтры, агрегации, векторный и гибридный поиск над хешами и JSON |
| **JSON** | `JSON.SET`, `JSON.GET`, `JSON.NUMINCRBY`, `JSON.ARRAPPEND` | Вложенные документы с обновлением по пути (JSONPath) |
| **Временные ряды** | `TS.CREATE`, `TS.ADD`, `TS.RANGE`, `TS.MRANGE` | Метрики, показания датчиков с агрегацией и политиками хранения |
| **Вероятностные структуры** | `BF.*`, `CF.*`, `CMS.*`, `TOPK.*`, `TDIGEST.*` | Bloom/Cuckoo filter, частоты, top-K, перцентили |
| **Vector Set** (ядро) | `VADD`, `VSIM` | Простой векторный поиск (модуль 6) |

Команды этого модуля требуют сборки с модулями (официальный образ `redis:8.10` их содержит), поэтому листинги ниже не входят в автоматические тесты курса.

## 19.2 JSON

```
JSON.SET user:1 $ '{"name":"anya","visits":0,"addresses":[{"city":"kazan"},{"city":"perm"}]}'
JSON.GET user:1 $.addresses[*].city          → ["kazan","perm"]
JSON.NUMINCRBY user:1 $.visits 1             → [1]
JSON.ARRAPPEND user:1 $.addresses '{"city":"sochi"}'
JSON.DEL user:1 $.addresses[0]
JSON.MGET user:1 user:2 $.name
```

JSON удобнее хеша для вложенных структур и обновления отдельных полей вложенных объектов, но тяжелее по памяти. В Redis 8.10 JSONPath заметно расширен: проекции, `in`/`nin`, арифметика, функции `length()`, `min()`/`max()`/`avg()`/`sum()`, `keys()`, `match()`/`search()`.

## 19.3 Поиск: индексы над хешами и JSON

```
FT.CREATE idx:products ON HASH PREFIX 1 product: SCHEMA
    name TEXT WEIGHT 2.0
    description TEXT
    price NUMERIC SORTABLE
    tags TAG SEPARATOR ","
    location GEO

HSET product:1 name "Ceramic mug" description "white mug 300 ml" price 450 tags "kitchen,gift" location "37.62,55.75"

FT.SEARCH idx:products "@name:mug @price:[100 500]" SORTBY price ASC LIMIT 0 10
FT.SEARCH idx:products "@tags:{gift} @location:[37.6 55.7 5 km]"
FT.AGGREGATE idx:products "*" GROUPBY 1 @tags REDUCE COUNT 0 AS n SORTBY 2 @n DESC
FT.INFO idx:products
```

- Индекс **обновляется автоматически** при изменении хешей или JSON-документов с нужным префиксом — не нужно поддерживать вторичные индексы вручную (модуль 7).
- Типы полей: `TEXT` (полнотекстовый, со стеммингом), `TAG` (точные значения), `NUMERIC`, `GEO`, `GEOSHAPE`, `VECTOR`.
- В кластере индекс распределён по шардам, запрос выполняет координатор.
- Это не замена Elasticsearch для сложной аналитики по сотням гигабайт текста, но для поиска по каталогу, фильтров и автодополнения рядом с данными — отличный вариант.

## 19.4 Векторный и гибридный поиск

```
FT.CREATE idx:docs ON HASH PREFIX 1 doc: SCHEMA
    title TEXT
    lang TAG
    embedding VECTOR HNSW 6 TYPE FLOAT32 DIM 384 DISTANCE_METRIC COSINE

HSET doc:1 title "Redis streams guide" lang en embedding <384 float32 в байтах>

FT.SEARCH idx:docs "(@lang:{en})=>[KNN 5 @embedding $vec AS score]"
    PARAMS 2 vec <байты вектора запроса> SORTBY score RETURN 2 title score DIALECT 2
```

`FT.HYBRID` (Redis 8.4) объединяет полнотекстовый и векторный поиск с объединением оценок (RRF или линейная комбинация) — так строят качественный поиск для RAG. Клиентская библиотека **RedisVL** (Python) упрощает схемы индексов, векторизацию и семантический кэш.

## 19.5 Redis в AI-приложениях

| Задача | Как в Redis |
|---|---|
| **Семантический кэш** ответов LLM | Вектор запроса → поиск похожего уже отвеченного → вернуть кэш, если близость выше порога |
| **RAG** | Векторный или гибридный поиск по чанкам документов с фильтрами по метаданным |
| **Память агента** | Хеши и JSON для фактов, потоки для истории диалога, векторы для поиска по памяти |
| **Ограничение частоты вызовов LLM** | `INCREX`, токен-бакет (модуль 10) |
| **Очередь задач для агентов** | Потоки с группами потребителей (модуль 5) |

## 19.6 Временные ряды и вероятностные структуры

```
TS.CREATE temp:sensor:1 RETENTION 604800000 LABELS sensor 1 room kitchen
TS.ADD temp:sensor:1 * 21.5
TS.RANGE temp:sensor:1 - + AGGREGATION avg 3600000
TS.MRANGE - + FILTER room=kitchen

BF.RESERVE seen:emails 0.001 10000000      # Bloom filter: 0,1% ложных срабатываний
BF.ADD seen:emails anya@example.com
BF.EXISTS seen:emails borya@example.com    # 0 — точно не было; 1 — вероятно было
TOPK.RESERVE top:queries 10
TOPK.ADD top:queries redis redis streams
```

## 19.7 Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| `ERR unknown command 'FT.SEARCH'` | Сборка Redis без модулей | Официальный образ Redis 8 или сборка с модулями |
| Поиск не находит новые документы | Префикс ключа не совпадает с `PREFIX` индекса | Проверить схему ключей и `FT.INFO` |
| Векторный поиск возвращает мусор | Размерность или тип вектора не совпадают со схемой, неверный порядок байт | Тот же `DIM` и `FLOAT32` little-endian, что в индексе |
| Память выросла после создания индекса | Индекс тоже занимает память | Индексировать только нужные поля, считать в планировании ёмкости |
| Тот же код не работает на Valkey | Модули Redis Query Engine и JSON — часть Redis | Проверять совместимость; у Valkey свои модули (`valkey-search`, `valkey-json`, `valkey-bloom`) |

### Практика

# Модуль 20. Redis в продакшене: Valkey, managed, Kubernetes, обновления

## 20.1 Redis или Valkey

| Критерий | Redis Open Source 8.x | Valkey 8–9 |
|---|---|---|
| Лицензия | RSALv2 / SSPLv1 / AGPLv3 на выбор | BSD |
| Кто развивает | Redis Ltd (с участием antirez) | Linux Foundation, AWS, Google, Oracle и другие |
| Совместимость с Redis 7.2 | Полная | Полная (форк от 7.2.4) |
| Новые команды из этого курса: `SET IFEQ`, `DELEX`, `INCREX`, `MSETEX`, `LMOVEM`, Array, Vector Set, `XNACK`, идемпотентный `XADD`, компактные хеши | Есть | Большинства нет; часть похожих возможностей реализована иначе |
| Время жизни полей хеша | С 7.4 | С Valkey 9.0 |
| Поиск, JSON, вероятностные структуры | Входят в Redis Open Source 8 | Отдельные модули `valkey-search`, `valkey-json`, `valkey-bloom` |
| Облака | Redis Cloud, Azure Managed Redis | AWS ElastiCache и MemoryDB, Google Memorystore, многие российские облака |

**Как выбирать:** если нужны новые возможности Redis 8 или Redis Cloud — Redis. Если важна BSD-лицензия, ваш облачный провайдер предлагает Valkey, а используются базовые структуры данных — Valkey. Код на базовых командах Redis 7.2 работает на обоих; для новых команд держи абстракцию в коде.

## 20.2 Managed или self-hosted

| | Managed | Self-hosted |
|---|---|---|
| Репликация, переключение, бэкапы, обновления | Из коробки | Сам: Sentinel или Cluster, бэкапы RDB, процесс обновлений |
| Ограничения | Часть команд и конфигурации недоступна (`CONFIG`, `DEBUG`, модули) | Полный контроль |
| Стоимость | Дороже за гигабайт памяти | Дешевле за ресурсы, дороже людьми |
| Когда | Нет экспертизы, важна скорость запуска | Особые требования к версии, модулям, сети, стоимости больших объёмов |

## 20.3 Redis в Kubernetes

- **StatefulSet** с постоянными томами (если включена персистентность), anti-affinity — мастер и реплики на разных узлах и в разных зонах, `PodDisruptionBudget`.
- **Лимит памяти контейнера больше `maxmemory`** с запасом 25–50% на буферы, фрагментацию и fork; иначе OOM-killer контейнера.
- **Операторы** управляют репликацией, Sentinel или Cluster и обновлениями (например, OT-Container-Kit redis-operator; у Redis есть коммерческий оператор для Redis Software). Простой кэш без персистентности можно держать и обычным Deployment.
- **Сеть**: Cluster объявляет клиентам адреса узлов — настрой `cluster-announce-ip`/`cluster-announce-hostname`, иначе клиенты вне кластера Kubernetes получат недоступные адреса.
- **Безопасность**: NetworkPolicy, ACL-пароли из секретов, TLS по требованиям.

## 20.4 Обновления

- **Минорные версии** (8.10.2 → 8.10.3) выходят часто и нередко содержат исправления безопасности — обновляйся быстро.
- **Порядок без простоя**: обновить реплики → переключиться (`SENTINEL FAILOVER` или `CLUSTER FAILOVER` на реплике) → обновить бывший мастер.
- **Формат RDB**: новая версия читает файлы старых, старая версия новые файлы читать не обязана — откат после того, как новый мастер записал RDB, может быть невозможен без промежуточной реплики старой версии.
- **Перед обновлением**: прочитай release notes (изменения поведения, удалённые и переименованные настройки), обнови клиентские библиотеки, прогони тесты и нагрузку на стенде.

## 20.5 Клиентские библиотеки

| Язык | Библиотеки |
|---|---|
| Python | redis-py (+ RedisVL для векторов) |
| Java | Jedis, Lettuce, Redisson (высокоуровневые структуры, блокировки) |
| Go | go-redis, rueidis (клиентское кэширование, пайплайны автоматически) |
| Node.js | node-redis, ioredis |
| .NET | StackExchange.Redis, NRedisStack |
| PHP, Ruby, Rust | phpredis/Predis, redis-rb, redis-rs |

Что настроить в клиенте: пул соединений с разумным размером, тайм-ауты подключения и команд, повторы только для идемпотентных операций, поддержка Sentinel или Cluster, RESP3 и клиентское кэширование, имена соединений (`CLIENT SETNAME`).

## 20.6 Антипаттерны

| Антипаттерн | Чем плох | Как лучше |
|---|---|---|
| Redis как единственное хранилище критичных данных без продуманной персистентности и реплик | Потеря данных при сбое | База данных — источник истины; Redis — ускорение и координация |
| `KEYS *` в коде | Блокирует сервер | `SCAN`, вторичные индексы |
| Ключи без TTL в кэше | Устаревшие данные, рост памяти | TTL всегда |
| Огромные коллекции в одном ключе | Задержки, проблемы в кластере | Разбиение ключей |
| Кэш, очереди и данные в одном экземпляре | Конфликт политик вытеснения и персистентности | Отдельные экземпляры |
| Новое соединение на каждый запрос | Накладные расходы, исчерпание соединений | Пул |
| Pub/Sub для задач, которые нельзя потерять | At-most-once | Потоки или списки с `LMOVE` |
| Блокировка как гарантия корректности финансовых операций | Пауза процесса, асинхронная репликация | Fencing tokens, инварианты в базе |
| Приложение под `default` со всеми правами | Любая ошибка может стереть всё | ACL с минимальными правами |
| Нет `maxmemory` | OOM-killer | `maxmemory` с запасом и политика |

## 20.7 Чек-лист готовности Redis к продакшену

| Область | Что должно быть |
|---|---|
| **Версия** | Поддерживаемая версия, последний минорный релиз с исправлениями безопасности |
| **Назначение** | Понятно, что это: кэш, очереди, данные, сессии; разные задачи — разные экземпляры |
| **Память** | `maxmemory` с запасом 20–30%, правильная политика вытеснения, алерты на память и вытеснение |
| **Данные** | TTL у кэша, нет огромных ключей, схема имён ключей, `SCAN` вместо `KEYS` |
| **Персистентность** | Осознанный выбор RDB/AOF, том для данных, бэкапы RDB вне сервера с проверкой восстановления |
| **Отказоустойчивость** | Реплики, Sentinel или Cluster (или managed), проверенное переключение, клиенты его переживают |
| **Безопасность** | Приватная сеть, ACL с минимальными правами, `default` выключен или с паролем, TLS по требованиям, опасные команды запрещены |
| **ОС** | `vm.overcommit_memory = 1`, THP отключены, нет свопа, лимиты соединений |
| **Клиенты** | Пулы, тайм-ауты, повторы, имена соединений, пайплайны для массовых операций |
| **Наблюдаемость** | redis_exporter, дашборд, алерты из модуля 18, SLOWLOG и LATENCY включены |

# Модуль 21. Итоговый проект: Redis-слой для сервиса онлайн-курсов

## 21.1 Что строим

Redis-слой для нагруженного сервиса онлайн-курсов: база данных (PostgreSQL) — источник истины, Redis отвечает за скорость, координацию и события в реальном времени.

```
 API ──► кэш карточек курсов (cache-aside, защита от лавины, клиентское кэширование)
  │ ──► сессии (хеши с TTL, TTL полей)
  │ ──► лимиты API (INCREX / токен-бакет), лимит попыток входа
  │ ──► таблица лидеров по баллам за неделю (ZSET), счётчики просмотров (HLL + INCR)
  │ ──► блокировка «одна генерация сертификата за раз» (SET NX PX + DELEX IFEQ)
  └──► поток событий learning-events ──► группы: achievements, notifications, analytics
                                              └── уведомления в реальном времени (sharded Pub/Sub)
 инфраструктура: кэш-экземпляр (allkeys-lfu, без персистентности) +
                 экземпляр данных (noeviction, AOF everysec) с репликами и Sentinel
```

## 21.2 Функциональные требования

1. **Кэш карточек курсов** — cache-aside с TTL 10 минут и джиттером, отрицательное кэширование несуществующих курсов, инвалидация при изменении курса, защита от «грохочущего стада» блокировкой на перестройку.
2. **Клиентское кэширование** справочников (категории, настройки, флаги функций) через RESP3 и `CLIENT TRACKING`.
3. **Сессии** — хеш `session:<id>` на 24 часа с продлением при активности; CSRF-токен с отдельным TTL 30 минут (`HEXPIRE`/`HSETEX`).
4. **Лимиты** — 100 запросов в минуту на пользователя (`INCREX`), 5 попыток входа за 15 минут с блокировкой, токен-бакет для дорогих запросов к LLM-помощнику.
5. **Прогресс и события** — каждое завершение урока пишется в поток `learning-events` с идемпотентным `XADD ... IDMP`; три группы потребителей: начисление достижений, уведомления, аналитика.
6. **Таблица лидеров** — баллы за неделю в `ZSET` по ключу недели, топ-100, место пользователя, итоги месяца через `ZUNIONSTORE`, «был в топе каждую неделю месяца» через `AGGREGATE COUNT`.
7. **Счётчики** — просмотры уроков (`INCR` по дням), уникальные зрители курса (HyperLogLog по дням и `PFMERGE` за месяц), активность по дням для «серии дней подряд» (битовые карты).
8. **Уведомления в реальном времени** — sharded Pub/Sub по каналу пользователя; при отсутствии подписчика уведомление остаётся в потоке уведомлений пользователя.
9. **Генерация сертификата** — одна генерация на пользователя и курс одновременно: блокировка с токеном, продлением и снятием через `DELEX IFEQ`; повторная генерация защищена уникальным ограничением в базе.
10. **Похожие курсы** — Vector Set с эмбеддингами описаний курсов и фильтром по языку.

## 21.3 Технические требования

11. **Два экземпляра**: кэш (`maxmemory` + `allkeys-lfu`, без персистентности) и данные (`noeviction`, AOF `everysec`, RDB-бэкапы во внешнее хранилище).
12. **Отказоустойчивость** экземпляра данных: мастер, две реплики, три Sentinel; клиенты подключаются через Sentinel.
13. **Атомарность**: все составные операции — транзакции, условные команды Redis 8 или функции, загружаемые при деплое (`FUNCTION LOAD REPLACE`).
14. **Ключи**: единая схема имён в одном модуле кода; ключи пользователя с hash tag `{user:<id>}` для будущего перехода на Cluster.
15. **Безопасность**: пользователи ACL для API, воркеров, аналитики и экспортера с минимальными правами; `default` выключен; `FLUSHALL`, `KEYS`, `CONFIG` запрещены приложениям.
16. **Тесты**: сценарии в стиле `run_tests.py` этого курса для лимитов, блокировок, таблицы лидеров и группы потребителей; нагрузочный тест `redis-benchmark` и тест приложения.
17. **Наблюдаемость**: redis_exporter, дашборд, алерты из модуля 18, доля попаданий кэша, отставание реплик, длина PEL каждой группы потребителей.

# Шпаргалка: ошибки и что делать

| Ошибка | Причина | Что делать |
|---|---|---|
| `WRONGTYPE Operation against a key holding the wrong kind of value` | Команда не для типа ключа | `TYPE`, раздельные имена ключей |
| `ERR value is not an integer or out of range` | `INCR` по нечисловому значению | Отдельный ключ счётчика |
| `OOM command not allowed when used memory > 'maxmemory'` | Память исчерпана при `noeviction` или нет ключей с TTL для `volatile-*` | Память, TTL, политика, разделение экземпляров |
| `NOAUTH Authentication required` | Не выполнен `AUTH` | Аутентификация в клиенте |
| `WRONGPASS invalid username-password pair or user is disabled` | Неверный пароль или выключенный пользователь | `ACL GETUSER`, пароль |
| `NOPERM ...` | Нет прав ACL на команду или ключ | `ACL DRYRUN`, обновить права |
| `MOVED <slot> <host:port>` | Кластер: ключ на другом узле | Кластерный клиент, `redis-cli -c` |
| `ASK <slot> <host:port>` | Слот мигрирует | Кластерный клиент |
| `CROSSSLOT Keys in request don't hash to the same slot` | Мультиключевая операция по разным слотам | Hash tags |
| `CLUSTERDOWN The cluster is down` | Слоты без мастера | Реплики, восстановление узлов |
| `READONLY You can't write against a read only replica.` | Запись на реплику (часто после переключения) | Подключение через Sentinel/кластерный клиент |
| `MISCONF Redis is configured to save RDB snapshots, but it's currently unable to persist to disk` | Неудачный `BGSAVE` | Диск, память, `vm.overcommit_memory` |
| `LOADING Redis is loading the dataset in memory` | Идёт загрузка RDB/AOF после старта | Подождать; учитывать в health checks |
| `BUSY Redis is busy running a script` | Долгий Lua-скрипт | `SCRIPT KILL`, короткие скрипты |
| `NOSCRIPT No matching script. Please use EVAL.` | Скрипта нет в кэше | `EVAL` или функции |
| `EXECABORT Transaction discarded because of previous errors.` | Ошибка при постановке команды в очередь `MULTI` | Исправить команду |
| `ERR max number of clients reached` | Достигнут `maxclients` | Пулы соединений, утечки соединений |
| `DENIED Redis is running in protected mode` | Внешнее подключение без пароля | ACL и `bind`, а не отключение защиты |
| `ERR unknown command 'FT.SEARCH'` | Сборка без модулей | Официальный образ Redis 8 |

# Вопросы на собеседовании по Redis с ответами

### Junior

1. **Что такое Redis и почему он быстрый?** Хранилище структур данных в памяти. Быстр, потому что данные в RAM, структуры эффективны, а команды выполняются в одном потоке без блокировок; сетевой ввод-вывод может идти в нескольких потоках.
2. **Какие типы данных есть в Redis?** Строки, списки, хеши, множества, сортированные множества, потоки, битовые карты и `BITFIELD`, HyperLogLog, геоиндексы, Vector Set (8.0), Array (8.8); в Redis Open Source 8 — также JSON, временные ряды и вероятностные структуры.
3. **Как задать время жизни ключа и что возвращает `TTL`?** `SET ... EX`, `EXPIRE`, `PEXPIRE`, `EXPIREAT`; `TTL` возвращает секунды, `-1` — без срока, `-2` — ключа нет.
4. **Почему нельзя использовать `KEYS` в продакшене?** Он обходит все ключи за один вызов и блокирует сервер. Нужен `SCAN` с курсором.
5. **Чем `DEL` отличается от `UNLINK`?** `DEL` освобождает память синхронно, `UNLINK` — в фоновом потоке, что важно для больших ключей.
6. **Как сделать атомарный счётчик?** `INCR`/`INCRBY` — атомарны; для счётчика с лимитом и сроком — `INCREX` (Redis 8.8).
7. **Как реализовать кэш на Redis?** Cache-aside: читаем кэш, при промахе — базу, кладём в кэш с TTL; при изменении данных удаляем ключ.
8. **Чем список отличается от множества?** Список упорядочен и допускает повторы, множество неупорядочено и хранит уникальные значения.
9. **Для чего сортированное множество?** Таблицы лидеров, приоритетные очереди, индексы по времени, скользящие окна, автодополнение.
10. **Что такое хеш и когда он лучше строки с JSON?** Набор полей под одним ключом; лучше, когда нужно читать и менять отдельные поля, увеличивать счётчики в объекте и задавать TTL полям.
11. **Что такое Pub/Sub?** Рассылка сообщений всем подписчикам канала, подключённым в момент публикации, без хранения.
12. **Что такое пайплайн?** Отправка многих команд без ожидания ответа на каждую — экономия сетевых кругов.
13. **Сохраняет ли Redis данные на диск?** Да, если настроено: снимки RDB и журнал AOF.
14. **Что такое `maxmemory` и политика вытеснения?** Предел памяти и правило, какие ключи удалять при его достижении (`noeviction`, `allkeys-lru`, `allkeys-lfu`, `volatile-*` и другие).
15. **Как обойти все ключи с префиксом?** `SCAN 0 MATCH prefix:* COUNT 1000`, повторяя до курсора `0`.
16. **Что такое `OBJECT ENCODING`?** Внутреннее представление значения: `int`, `embstr`, `listpack`, `hashtable`, `intset`, `skiplist`, `quicklist`.

### Middle

17. **Как работают транзакции `MULTI`/`EXEC` и почему в них нет отката?** Команды ставятся в очередь и выполняются подряд без вклинивания других клиентов. Ошибки выполнения не откатывают остальные команды; синтаксические ошибки отменяют транзакцию целиком.
18. **Что делает `WATCH`?** Оптимистичная блокировка: если наблюдаемый ключ изменился до `EXEC`, транзакция не выполняется (`(nil)`), клиент повторяет цикл.
19. **Зачем Lua-скрипты и функции и чем они отличаются?** Атомарное выполнение логики на сервере. Функции (7.0) именованы, хранятся на сервере, попадают в RDB/AOF и реплицируются; `EVAL`-скрипты живут в кэше и теряются при перезапуске.
20. **Почему ключи в Lua передают через `KEYS`?** Чтобы сервер и кластер знали, к каким ключам и слотам обращается скрипт.
21. **Как сделать распределённую блокировку на Redis?** `SET lock token NX PX ttl`, снятие только своей — сравнение токена и удаление атомарно (`DELEX ... IFEQ` в Redis 8.4 или Lua), продление для долгой работы.
22. **Какие проблемы у блокировок на Redis и что такое fencing token?** Пауза процесса дольше TTL или переключение на реплику дают двух владельцев. Fencing token — монотонный номер, по которому хранилище отвергает запись устаревшего владельца.
23. **Как сделать ограничение частоты?** Фиксированное окно (`INCREX` или `INCR` + `EXPIRE`), скользящее окно на ZSET в Lua, токен-бакет в Lua.
24. **Что такое cache stampede и как защититься?** Массовые промахи по истёкшему горячему ключу. Блокировка на перестройку, мягкий и жёсткий срок, вероятностное раннее обновление, джиттер TTL.
25. **Почему при изменении данных ключ кэша удаляют, а не обновляют?** Конкурентные обновления могут записать старое значение последним; удаление гарантирует перечитывание из базы.
26. **Что такое клиентское кэширование?** Клиент хранит значения у себя, а сервер присылает инвалидации при изменении ключей (`CLIENT TRACKING`, RESP3 или `REDIRECT`).
27. **Чем потоки отличаются от списков и Pub/Sub?** Хранят историю, позволяют читать с любого места, имеют группы потребителей с подтверждениями (`XACK`), PEL и повторной доставкой.
28. **Что такое PEL и как вернуть сообщения упавшего потребителя?** Список выданных, но не подтверждённых сообщений группы. Возврат — `XAUTOCLAIM`/`XCLAIM`; `XNACK` (8.8) позволяет потребителю освободить сообщение самому.
29. **Какие гарантии доставки у потоков?** At-least-once: обработчики должны быть идемпотентными; повтор записи производителем — `XADD ... IDMP` (8.6).
30. **Что такое кодировка `listpack` и почему у неё порог?** Компактное непрерывное представление маленьких коллекций; операции в нём O(N), поэтому при росте коллекция переходит в полную структуру.
31. **Что такое большой и горячий ключ?** Большой — огромная коллекция или строка, операции над ним долгие; горячий — непропорционально много запросов, в кластере перегружает один узел.
32. **Что такое HyperLogLog?** Вероятностный счётчик уникальных элементов: до 12 КБ на любой объём с погрешностью ~0,81%.
33. **Чем RDB отличается от AOF?** RDB — периодический снимок (быстрый старт, потеря минут); AOF — журнал команд с `fsync` раз в секунду (потеря до секунды).
34. **Какие условные команды появились в Redis 8?** `SET ... IFEQ/IFNE/IFDEQ/IFDNE`, `DELEX` (8.4), `INCREX` (8.8), а также `MSETEX`, `HSETEX`/`HGETEX`, `LMOVEM` и другие.

### Senior

35. **Как работает `BGSAVE` и почему растёт память?** `fork` создаёт дочерний процесс со снимком памяти через copy-on-write; при записи изменённые страницы копируются, в худшем случае удваивая память. Нужны запас памяти, `vm.overcommit_memory = 1`, отключённые THP.
36. **Как работает репликация и что гарантирует `WAIT`?** Асинхронный поток команд от мастера, полная синхронизация через RDB и частичная из `repl-backlog`. `WAIT` ждёт подтверждения N реплик и уменьшает окно потерь, но не даёт строгой консистентности.
37. **Как Sentinel выполняет переключение?** Sentinel'ы договариваются кворумом, что мастер недоступен, выбирают лидера, повышают лучшую реплику, перенастраивают остальные и сообщают клиентам новый адрес.
38. **Что такое split brain и как его ограничить?** Отрезанный старый мастер принимает записи, которые будут потеряны. Ограничивают `min-replicas-to-write` и `min-replicas-max-lag`.
39. **Как устроен Redis Cluster?** 16 384 хеш-слота по CRC16 ключа распределены между мастерами с репликами; клиенты получают `MOVED`/`ASK`; мультиключевые операции — только в одном слоте.
40. **Зачем hash tags и в чём их опасность?** `{tag}` задаёт слот по части имени, позволяя мультиключевые операции. Неудачный тег с низкой кардинальностью создаёт перекос нагрузки.
41. **Какие источники задержек в Redis?** Медленные команды O(N), большие ключи, долгие скрипты, fork, своп, массовое истечение ключей, сеть и отсутствие пайплайнов, исчерпание соединений.
42. **Как диагностировать «Redis тормозит»?** `--latency` с клиента и сервера, `SLOWLOG`, `INFO commandstats`, `LATENCY DOCTOR`, `INFO memory` (своп, фрагментация), `CLIENT LIST`, CPU основного потока, изменения в нагрузке.
43. **Как выбрать политику вытеснения и персистентность для разных задач?** Кэш — `allkeys-lfu`/`lru` без персистентности; данные и очереди — `noeviction`, AOF `everysec`, реплики; разные задачи — разные экземпляры.
44. **Что такое фрагментация памяти и как с ней работать?** Разница между `used_memory_rss` и `used_memory`; лечится активной дефрагментацией или перезапуском реплики с переключением; коэффициент меньше 1 — своп.
45. **Как защитить Redis?** Приватная сеть, ACL с минимальными правами, выключенный `default`, TLS, запрет опасных команд и изменения защищённых настроек, своевременные обновления безопасности.
46. **Как масштабировать Redis?** Чтение — реплики и клиентское кэширование; память и запись — Cluster; сеть — пайплайны; горячие ключи — локальный кэш и разделение ключей.
47. **Чем Redis 8 отличается от Valkey и как выбирать?** Лицензии (RSAL/SSPL/AGPL против BSD), новые команды и типы Redis 8, встроенные поиск и JSON; Valkey — выбор облаков и BSD. Базовые команды совместимы.
48. **Как сделать надёжную очередь с отложенными задачами?** ZSET со временем запуска, атомарный перенос наступивших задач в список или поток Lua-функцией, обработка с подтверждением, возврат зависших, идемпотентные обработчики.
49. **Как обновить Redis без простоя?** Обновить реплики, переключиться через Sentinel или `CLUSTER FAILOVER`, обновить бывший мастер; учесть, что старые версии могут не читать RDB новых.
50. **Как бы ты спроектировал Redis-слой нагруженного сервиса?** Разделить экземпляры кэша и данных, cache-aside с защитой от лавины и клиентским кэшированием, лимиты на `INCREX` и токен-бакете, события в потоках с группами и идемпотентностью, блокировки с токенами для эффективности, инварианты — в базе, Sentinel или Cluster, ACL, мониторинг. Подробно — модуль 21.

# FAQ: частые вопросы про Redis

**Redis — это база данных или кэш?**
И то, и другое, но в первую очередь — хранилище структур данных в памяти. Для критичных данных источником истины обычно остаётся база данных.

**Можно ли потерять данные в Redis?**
Да: без персистентности — при любом перезапуске; с AOF `everysec` — до секунды записей; при переключении на асинхронную реплику — недоставленные записи. Это нужно учитывать в архитектуре.

**Сколько данных может хранить Redis?**
Столько, сколько памяти дадите (с запасом 20–30%). Больше одной машины — Redis Cluster.

**Сколько операций в секунду выдерживает Redis?**
Сотни тысяч простых операций на ядро; с пайплайнами и многопоточным вводом-выводом — больше. Реальная цифра зависит от команд, размера значений и сети.

**Redis однопоточный?**
Выполнение команд — в одном потоке. Сетевой ввод-вывод, освобождение памяти, fsync и сохранение — в других потоках и процессах.

**Нужно ли использовать несколько баз (`SELECT`)?**
Лучше нет: это не изоляция, а в Cluster есть только база 0. Разные приложения — разные экземпляры или префиксы и ACL.

**Как хранить объекты: JSON в строке, хеш или JSON-тип?**
Кэш объекта целиком — строка с JSON; объект с частыми изменениями отдельных полей — хеш; вложенные документы с поиском — JSON-тип.

**Что выбрать для очереди: список, поток или брокер?**
Простая очередь задач — список с `BLMOVE` или готовая библиотека; несколько групп обработчиков и подтверждения — поток; долгое хранение и огромные объёмы — Kafka.

**Подходит ли Redis для распределённых блокировок?**
Для эффективности (не делать работу дважды) — да. Для корректности критичных операций — только с fencing tokens или с защитой инварианта в базе.

**Redis или Memcached?**
Redis почти всегда: богаче структуры, персистентность, репликация. Memcached проще и многопоточный, но умеет только строки.

**Redis или Valkey?**
Новые возможности Redis 8 и Redis Cloud — Redis; BSD-лицензия и облачный провайдер с Valkey — Valkey. Базовые команды совместимы.

**Как переименовать опасные команды?**
Современный способ — ACL (`-@dangerous`, `-flushall`), а не `rename-command`.

**Почему `INFO` показывает `mem_fragmentation_ratio` меньше 1?**
Часть памяти Redis в свопе — это авария для задержек; убери своп и добавь память.

**Где учиться дальше?**
Официальная документация redis.io (раздел Develop и справочник команд с указанием сложности), блог antirez, книга «Redis in Action» (устарела в деталях, но хороша по паттернам), исходники Redis — они читаются на удивление легко.

# Глоссарий Redis

| Термин | Определение |
|---|---|
| **ACL** | Списки управления доступом: пользователи, пароли, разрешённые команды, ключи и каналы |
| **AOF** | Append Only File — журнал команд записи для восстановления |
| **Array** | Тип Redis 8.8: разреженный массив с доступом по индексу |
| **Big key** | Ключ с огромной коллекцией или строкой |
| **Bitmap** | Строка как массив битов |
| **Cache-aside** | Стратегия кэширования «читай кэш, при промахе — источник» |
| **Cache stampede** | Лавина запросов в источник при истечении горячего ключа |
| **Client-side caching** | Кэш на стороне клиента с инвалидацией от сервера |
| **Cluster** | Шардирование по 16 384 хеш-слотам с автоматическим переключением |
| **Consumer group** | Группа потребителей потока, делящая сообщения между собой |
| **Copy-on-write** | Механизм fork: страницы памяти копируются только при изменении |
| **Encoding** | Внутреннее представление типа (`listpack`, `hashtable`, `skiplist`...) |
| **Eviction** | Вытеснение ключей при достижении `maxmemory` |
| **Fencing token** | Монотонный номер блокировки для защиты от устаревших владельцев |
| **Function** | Lua-функция, хранимая на сервере (Redis 7.0) |
| **Hash slot** | Один из 16 384 слотов кластера, определяется CRC16 ключа |
| **Hash tag** | Часть имени ключа в `{}`, по которой вычисляется слот |
| **Hot key** | Ключ с непропорционально большим числом обращений |
| **HyperLogLog** | Вероятностный счётчик уникальных элементов |
| **Keyspace notifications** | События о ключах через Pub/Sub |
| **Lazy free** | Освобождение памяти в фоновом потоке (`UNLINK`, `lazyfree-*`) |
| **LFU, LRU, LRM** | Вытеснение по частоте, давности чтения, давности изменения |
| **Listpack** | Компактная непрерывная кодировка маленьких коллекций |
| **MOVED, ASK** | Перенаправления клиента в кластере |
| **PEL** | Pending Entries List — выданные, но не подтверждённые сообщения группы |
| **Pipeline** | Отправка пачки команд без ожидания каждого ответа |
| **Pub/Sub** | Рассылка сообщений подписчикам без хранения |
| **Quicklist** | Кодировка списка: связный список узлов listpack |
| **RDB** | Снимок данных на диске |
| **Redlock** | Алгоритм блокировки на нескольких независимых Redis |
| **Replica** | Копия мастера, обновляемая асинхронно |
| **repl-backlog** | Буфер мастера для частичной синхронизации реплик |
| **RESP2, RESP3** | Версии протокола Redis; RESP3 добавляет типы и push-сообщения |
| **Sentinel** | Система мониторинга и автоматического переключения |
| **Sharded Pub/Sub** | Pub/Sub с каналами, привязанными к слотам кластера |
| **Skiplist** | Структура упорядоченного доступа внутри сортированных множеств |
| **SLOWLOG** | Журнал команд дольше порога |
| **Split brain** | Два мастера после сетевого разделения |
| **Stream** | Журнал записей с ID и группами потребителей |
| **TTL** | Время жизни ключа или поля хеша |
| **Valkey** | Форк Redis 7.2 под BSD от Linux Foundation |
| **Vector Set** | Тип Redis 8.0 для векторов и поиска похожих (HNSW) |
| **WATCH** | Оптимистичная блокировка ключей перед транзакцией |
